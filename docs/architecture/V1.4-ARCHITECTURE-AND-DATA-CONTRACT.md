# v1.4 architecture and data preservation

**Status:** Agreed product direction and technical design constraints. Backend, database schema and implementation are not yet approved. This is the concise active reference for [#105](https://github.com/Caffoot/Caffoot-Lite/issues/105), distilled from draft PR #50 and the [v1.4 roadmap](../roadmaps/V1.4-FOUNDATION-AND-RELEASE-PLAN.md). Published v1.3.3 and its Git history are the fallback.

## Product and deployment

- One Caffoot Lite product. v1.4 is a Docker-hosted, database-backed evolution of the published standalone v1.3.3 application.
- Reuse the proven HTML/CSS/JavaScript interface and existing Devices, IPAM, racks, charts and inventory workflows. Avoid a new frontend framework without a demonstrated need.
- Aim for one easy-to-install Docker Compose or Portainer stack, one application container where practical, persistent storage, no publicly exposed database port, AMD64 and ARM64 Raspberry Pi 5 support.
- The existing standalone HTML is a historical published release, not an alternative actively developed v1.4 deployment.
- Security should be proportionate to infrastructure inventory data: secure administrator enrolment, agreed MFA/recovery, backend-enforced access controls, protected sessions/secrets, safe defaults and reverse-proxy guidance. A reverse proxy alone is not application security.

## Data boundaries

Keep these logical domains distinct, without assuming each needs a separate database: inventory (devices, IPAM, VLANs, racks and accessories); stable entity identity and legacy-ID mappings; per-user/browser presentation preferences; safety snapshots and restore staging; audit/history; server-side users/authentication and secrets; deployment configuration. Later tenant/site/address-domain support is proposed, not implemented.

The published standalone application uses browser-local `caffoot_state` and versioned JSON backups. In v1.4 the server becomes the authoritative inventory store. Do not silently synchronise, overwrite or remove the user's original browser inventory. Do not put passwords, MFA secrets or session tokens in portable inventory exports.

## Identity and migration contract

1. Preserve existing device, rack, subnet, VLAN, accessory and related IDs, custom fields, links and historical data. Existing `deviceId`, `reservedForDeviceId`, `rackId`, `parentId` and `virtualHostId` relationships must survive migration.
2. Distinguish immutable internal IDs, retained legacy IDs and optional human-readable asset tags. UUIDs and numbering policies are proposals until the schema is approved; never silently renumber or merge assets based on hostname, IP or label.
3. Keep supported historical unversioned and schema-v1 JSON imports working. Application version, internal state version, database migration version and interchange schema version are separate.
4. Import into a detached, validated candidate, retaining an untouched source copy. Check duplicates, broken references, device/IPAM consistency, virtual-host relationships, rack occupancy and hierarchy before committing. Failure must leave the original usable.
5. Store any generated identity mapping durably. Repeated migration must be idempotent. Verify a committed migration by reading it back; provide recovery/rollback. Import is replacement, not an implicit merge.
6. Preserve portable, user-restorable exports separately from database snapshots. Test interrupted writes, rejected inputs and actual restore before release.

## Backend and database decision

SQLite is a simplicity candidate for a single-host installation; PostgreSQL offers different concurrency and operational trade-offs. **Neither has been selected.** Choose the smallest solution that safely supports the agreed simultaneous users, transactions, migration, backup and recovery. Device/IPAM and rack mutations must remain consistent. Do not invent a multi-tenant schema, clustered deployment or speculative feature architecture.

## Release boundaries and evidence

The first v1.4 release is the Docker/database foundation with existing functionality and safe migration, not ticketing, email, directory integration or every future feature. Subsequent scope belongs in the [current roadmap](../../ROADMAP.md). Reuse existing v1.3.3 tests where valid; run focused tests for new backend, permissions, migration, backup/restore and deployment behaviour. Documentation inspection is not executed test evidence.

Historical detailed design discussions remain in [draft PR #50](https://github.com/Caffoot/Caffoot-Lite/pull/50) and Git history. Resolve outstanding technical decisions with the product owner before changing application behaviour.

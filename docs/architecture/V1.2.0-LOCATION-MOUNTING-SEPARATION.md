# v1.2.0 — Separate Physical Location from Rack Mounting

Status: architecture and migration checklist. Application behaviour is not changed by this document.

## Problem confirmed in current source

`device.location === 'Racked'` is currently a sentinel for rack mounting, even though the UI also has `device.mountType === 'Rack Mounted'` and rack placement fields. Selecting Rack Mounted forces and disables the Location Area selector. Saving and imported-state validation enforce the sentinel. Rack move/unassign flows overwrite location; rack inventory display derives a label from it. The default location list includes protected `Racked`.

## Target meaning

- `location`: user-managed physical site, building, room or area; may be `Unknown` if not known.
- `mountType`: physical mounting method (including `Rack Mounted`).
- `rackId`, `face`, `rackUStart`, `rackUEnd`, `rackUHeight`: rack assignment, valid only for rack-mounted devices.
- Rack assignment never overwrites a meaningful physical location.
- A rack-mounted device may have any valid physical location (including Unknown); rack geometry and ownership remain independently validated.

## Compatibility and migration policy

1. Preserve existing real physical locations verbatim.
2. On reading legacy state or backups, convert only the exact legacy sentinel `Racked` on rack-mounted devices to `Unknown`, retaining rack ID, face and U placement. Never infer a site from rack name.
3. Existing non-rack devices marked `Racked` are inconsistent legacy records: handle with explicit compatibility validation/repair rather than silently assigning a rack.
4. Make migration idempotent. Do not mutate the source backup or the active inventory if import validation fails.
5. Preserve compatibility with schema-v1 and legacy backup fixtures. Do not change exported schema solely for this fix unless tests show it necessary.
6. Keep `Unknown` as a supported location; stop offering `Racked` as a new location once migration is in place. Existing managed lists need a safe cleanup rule, not a blind delete.
7. Any rack move, unassign or resize must preserve the physical location; when rack assignment is removed, clear only rack placement data and update mounting as appropriate.

## Implementation sequence (separate, reviewable increments)

1. Add focused regression fixtures for rack-mounted devices with meaningful physical locations, legacy `Racked` migration, imported backups, rack moves, unassign, edit, duplicate, and failed-save rollback.
2. Add a single compatibility normalization path before validation, with safe cloning/rollback and no guessed locations. Audit all state entry points.
3. Remove `location === 'Racked'` checks from rack validation and saving, replacing them with explicit mounting/rack invariants.
4. Remove the UI forced-location and disabled-control behaviour; let users select physical locations independently. Handle cross-tab validation and tab focus.
5. Update rack inventory and detail labels, location manager, defaults and rack move/unassign flows. Retain legacy import support.
6. Run all npm release checks, inspect generated offline HTML, and manually verify PowerShell/browser workflows in light and dark themes. Verify legacy and current backups round-trip before merge.

## Acceptance scenarios

- London Office + Rack Mounted + Comms Rack 01 + U12–U13 saves and reloads without changing London Office.
- Switching mounting methods does not overwrite a chosen site/room.
- A legacy record with location `Racked` and valid rack geometry loads as Unknown location, with rack placement unchanged.
- Rack move/unassign does not erase site/room.
- Invalid or overlapping rack placement is still rejected.
- Import failure does not modify existing inventory.
- No change to IPAM allocations or standalone offline operation.

Do not merge or release until implementation and tests are verified.

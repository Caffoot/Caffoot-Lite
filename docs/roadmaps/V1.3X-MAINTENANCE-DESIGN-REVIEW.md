# v1.3.x maintenance design review

**Status:** Design review in progress. **Recorded:** 24 October 2026. **Working branch:** `docs/post-pr89-status-reconciliation`. **Published baseline:** v1.3.0. **Scope:** v1.3.1, v1.3.2 and v1.3.3 proposals.

## Purpose and agreed process

The product owner agreed to **complete a structured design review of the outstanding maintenance findings before starting planned implementation**. This is the controlling plan for the review, not authorisation to change application behaviour.

For each roadmap finding:

1. **Understand:** Check the current main branch source, released behaviour where relevant, existing policies, technical workflow, test evidence and open findings. Explain the current behaviour in plain British English.
2. **Discuss and agree:** Identify the problem, user experience, desired behaviour, legacy and custom data protection, dependencies and edge cases. Record explicit product owner decisions separately from suggestions.
3. **Document:** Update the findings programme, applicable technical workflows, device and software compatibility matrix, roadmap and this review record. Mark proposed behaviour distinctly from current behaviour.
4. **Plan verification:** Define unit, integration and browser scenarios, including save failure, cancellation, migration and historical inventory cases. Never mark a test passed unless executed.
5. **Reconcile:** Check cross references and master audit status after each meaningful checkpoint, recording incomplete items explicitly.
6. **Prioritise:** Allocate work to the appropriate maintenance release based on safety, dependencies and scope.

Once all findings have an agreed outcome, **return to the beginning** and produce an implementation order, with separate owner approval for each behaviour change. Implement in small batches, verify and document each batch, reconcile statuses, then seek explicit approval before merging or releasing. Urgent inventory safety risks can be escalated for an earlier separately approved correction.

## Agreed device purpose and deployment design, 24 October 2026

**Product owner decision:** For suitable device categories, the Add/Edit Device form should ask separately **what the device is** (for example server, firewall, NAS, router) and **how it runs** (Physical or Virtual). Show only relevant follow-on fields. A virtual firewall can therefore remain classified as a firewall, with a physical hypervisor host and its own guest OS, rather than being forced into a virtual server type. This is a design agreement, not implemented behaviour.

**Physical server host control:** Offer a clearly worded option such as **This device hosts virtual machines**. When enabled, reveal a hypervisor product selector and separate version selector, and synchronise the existing Hypervisor server service rather than allowing contradictory independent controls. Virtual devices select an eligible physical server and inherit its hypervisor platform, while retaining their own operating system and version. Keep unassigned virtual devices possible under the previously agreed safeguards.

**Simplicity and compatibility:** Keep a single Add/Edit form with progressive disclosure, sensible defaults and clear language. Do not require every device type to support virtual deployment. Initially retain the agreed eligible host rule for physical servers, pending explicit design review for any additional host categories. Existing `Server - Physical` and `Server - Virtual` values, legacy/custom types, imports, device relationships and historical software selections must remain readable and editable. Determine a non-destructive storage and migration approach before implementation. Do not rename persisted types merely to change labels.

**Verification needed:** Source trace all type specific form sections and storage fields; design scenarios for physical/virtual switching, virtual firewall and NAS, guest OS independence, host eligibility, cancelled edits, failed saves, conversions and legacy imports. Update WF-03, WF-06, WF-07, WF-08, findings, compatibility matrix and master audit status through reconciliation. No application change or browser test authorised by this agreement.

## Approved design direction: virtual desktops, 24 October 2026

The product owner agreed to support **Desktop → Physical or Virtual** for the small business inventory use case. Physical is the default. Virtual desktop records may select an eligible physical hypervisor host and must retain their own guest operating system and version, independently of the host platform. Laptop and Tablet remain physical only initially. This is **inventory recording**, not VDI management or VM operation. Preserve all existing desktop records and historical imports. The physical or virtual selector must not impose extra complexity on ordinary users. Implementation and any storage migration still require separate approval.

**Status:** Design agreed; source verification of desktop field handling, host selection, conversion, imports and test coverage remains outstanding. No tests executed or application behaviour changed.

## Superseding decision: Desktop and Virtual Desktop, 24 October 2026

**Product owner revision:** The earlier proposal to offer Physical and Virtual deployment within the `Desktop` type is **superseded**. Keep `Desktop` **physical only** and introduce a distinct `Virtual Desktop` device type that is **virtual only**. `Laptop` and `Tablet` remain physical only. The Add/Edit form should infer deployment from the selected type for these categories, avoiding a redundant Physical or Virtual question. Virtual Desktop shows eligible host selection, independent guest OS and version, and the relevant VM fields. Reuse the underlying virtual host validation and relationship safeguards rather than duplicate logic.

**Compatibility and implementation boundary:** Do not silently rewrite or discard existing Desktop records, including any imported or custom virtualisation fields. Investigate legacy data and device type registration, validation, conversion and import/export before coding. This explicit type approach for desktops does not overturn the separately agreed purpose and deployment design for suitable devices such as firewalls and NAS. Design agreed only; no application change or release approval. Test matrices and master audit reconciliation remain outstanding.

## Agreed user experience principle: infer what is already known, 24 October 2026

**Product owner approved principle:** **Do not ask users a question when their selected device type already tells us the answer.** In the Add/Edit Device form, derive fixed characteristics from the device type and show only genuinely necessary choices. For example, Desktop is physical only and Virtual Desktop is virtual only, so neither requires a redundant deployment question. For categories where physical and virtual are both valid, show a simple choice only when necessary. Use progressive disclosure, clear everyday language and sensible defaults, without hiding important information or making changes without user confirmation.

Apply this principle when reviewing all device types, operating system suggestions, host relationships, service controls, catalogue selectors and common form actions. It is a **design rule**, not permission to change stored device values or application behaviour. Preserve legacy, imported and custom records. Check any exception against real user needs before adding fields. Cross reference this rule during WF-03, WF-07 and WF-08 verification planning.

**Checkpoint:** Documentation decision only; no browser tests or code changes. Findings, workflows, test matrices and master audit reconciliation remain open.

## Agreed deployment design: Firewall, Router and NAS, 24 October 2026

**Product owner decision:** Keep **one device type each** for Firewall, Router and NAS. Each offers a simple **Physical or Virtual** deployment choice, because both are valid. Do not create separate physical and virtual device type labels for these categories. Physical shows relevant hardware fields; Virtual shows eligible hypervisor host selection and the device's own operating system and version. Hypervisor platform derives from the host, not a contradictory independent virtual field. This contrasts deliberately with Desktop (physical only) and Virtual Desktop (virtual only), where no deployment question is necessary.

**Constraints:** Preserve all existing Firewall, Router and NAS records and imported/custom values. Investigate default for existing records, host eligibility, safe deployment changes, legacy imports, NAS storage array fields, and validation before implementation. The design is agreed, but application changes still require separate product owner approval. Browser verification and documentation reconciliation remain outstanding.

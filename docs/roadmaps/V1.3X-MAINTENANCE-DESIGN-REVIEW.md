# v1.3.x maintenance design review

**Status:** Design review in progress. **Recorded:** 24 October 2026. **Working branch:** `docs/post-pr89-status-reconciliation`. **Published baseline:** v1.3.0. **Scope:** v1.3.1, v1.3.2 and v1.3.3 proposals.

## Purpose and agreed process

The product owner agreed to **complete a structured design review of the outstanding maintenance findings before starting planned implementation**. This is the controlling plan for the review, not authorisation to change application behaviour.

For each roadmap finding:

1. **Understand:** Check the current main branch source, released behaviour where relevant, existing policies, technical workflow, test evidence and open findings. Explain the current behaviour in plain British English.
2. **Discuss and agree:** Identify the problem, user experience, desired behaviour, legacy and custom data protection, dependencies and edge cases. Record explicit product owner decisions separately from suggestions.
3. **Document:** Update the findings programme, applicable technical workflows, device and software compatibility matrix, roadmap and this review record. Mark proposed behaviour distinctly from current behaviour.
4. **Plan verification:** Define unit, integration and browser scenarios, including save failure, cancellation, migration and historical inventory cases. Never mark a test passed unless executed.
5. **Reconcile:** Check cross references and master audit status after each meaningful checkpoint, recording incomplete items explicitly.
6. **Prioritise:** Allocate work to the appropriate maintenance release based on safety, dependencies and scope.

Once all findings have an agreed outcome, **return to the beginning** and produce an implementation order, with separate owner approval for each behaviour change. Implement in small batches, verify and document each batch, reconcile statuses, then seek explicit approval before merging or releasing. Urgent inventory safety risks can be escalated for an earlier separately approved correction.

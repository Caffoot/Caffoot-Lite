# Caffoot Lite v1.3.1 Maintenance Roadmap

**Status:** Candidate investigation register. No v1.3.1 changes approved or implemented.
**Baseline:** Published v1.3.0 HTML at tag `v1.3.0`, commit `92d6a60b0e4bc9f73589b27820cb283def377dbd`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`. Other packaged assets and runtime tests remain separate checks.
**Purpose:** Capture potential defects, missing safeguards and maintenance improvements found while documenting the actual v1.3.0 application. This document does not assert that any candidate is a confirmed defect.

## Rules

- Preserve an accurate description of v1.3.0 in `docs/workflows/TECHNICAL-WORKFLOWS.md`; do not silently rewrite historical behaviour.
- Record source evidence, reproduction steps, risk, dependencies and test requirements before confirming an issue.
- Distinguish **Investigation required**, **Confirmed issue**, **Approved for v1.3.1**, **Fixed and verified**, and **Closed without change**.
- Prioritisation and inclusion in v1.3.1 require product owner approval. No application code changes are authorised by this roadmap.
- Keep the published v1.3.0 application untouched unless separate maintenance work is explicitly approved.
- Use British English in public-facing text.

### Additional candidate: M-009 Gateway ownership and subnet editing

**Status:** Investigation required, source-supported scenario, runtime reproduction pending.

The device primary IP helper permits a gateway address on Firewall, Router and Layer 3 Switch devices, while the subnet form rejects any proposed gateway already recorded as a device primary IP or IPAM allocation, including when the gateway value is unchanged. Test whether editing an unrelated subnet field fails when its gateway is legitimately device-owned. Decide and document gateway ownership rules before approving a fix; preserve existing data and add regression tests.

**M-009 additional source evidence:** `phase10GatewaySubnet()` identifies a gateway directly from the subnet record, and `phase10SubnetSummary()` counts an unallocated gateway as reserved without storing an IPAM allocation. `setDevicePrimaryIp()` permits eligible network devices to own a gateway and creates a device-linked allocation. The subnet editor nevertheless rejects any proposed gateway already device-owned or present in IPAM, even when unchanged. Verify via browser testing after documentation; consider legacy and imported inventories before approving behaviour changes.

**M-005 import evidence:** `normaliseState()` and `validateApplicationState()`, both used during backup import, have no explicit `virtualHostId` relationship validation. Test an imported virtual server referring to a missing or no-longer-physical host. Determine desired rejection, warning or controlled recovery behaviour before implementing anything.

**M-009 import evidence:** Imported network gateways are checked for validity and membership in their subnet, but the shared integrity validator does not explicitly enforce permitted device types for a device owning that gateway. Test gateway ownership across imported legacy inventories and manual edits before agreeing one consistent policy.

### M-012: Integrity repair snapshot verification and failed-save recovery

**Status:** Investigation required. Source observation only; no reproduced data loss or approved fix.

**Evidence:** `phase11CApplyRepair()` stores `caffoot_phase11c_pre_repair_v1` before mutating IPAM but does not explicitly compare a readback of that snapshot. If a subsequent operation throws or `saveState()` reports failure, the handler restores the prior in-memory inventory and attempts to reinstate the previous snapshot, silently ignoring an error in that reinstatement. This catch path does not independently verify the main inventory storage or snapshot. `saveState()` separately validates and checks exact main-inventory readback on its success path.

**Next step:** Test in a disposable browser profile with storage failures before and after snapshot writes and during the main inventory save. Establish whether the existing safeguards are sufficient, what remains recoverable and whether snapshot readback or additional failure reporting would improve protection. Preserve compatibility and seek approval before any change.


### M-013: Include rack accessories in occupancy reporting

**Status:** Product owner suggested improvement; requirements and implementation not yet approved.

**Current v1.3.0 source behaviour:** `phase10DReportData()` calculates front and rear rack occupancy by summing mounted device U ranges only. Rack accessories are not included in the report's occupancy calculation. Source: `app/caffoot-lite.html`, `main`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`.

**Proposed behaviour for review:** Count horizontal rack accessories that consume U positions, alongside devices, on the relevant face. Track vertical or side-mounted accessories separately without treating them as horizontal U consumption. Calculate occupied positions as a union of valid occupied U slots per face rather than summing heights, to avoid double counting. Retain clear front and rear totals and agree whether a single overall rack percentage should represent maximum face occupancy. Do not assume every accessory consumes U space; inspect actual accessory types and placement schema first.

**Investigation and tests:** Trace accessory records, rack placement and face semantics; compare rack graphics and free-space calculations; test mixed devices and accessories, overlapping or imported legacy records, front/rear separation, side rails, and empty racks. Confirm the intended capacity definition with the product owner before implementation. Update report UI, CSV, tests and technical workflows together if approved. No application changes authorised.


**Additional WF-05 source evidence, 22 October 2026:** Published v1.3.0 `phase10DReportData()` (approximately lines 2305–2336) supplies both the Reports view and the Racks CSV. It sums device U heights by `face`, omits horizontal accessories and can double count overlapping imported records. The maximum of front/rear counts defines the report percentage and should not be changed without an explicit product decision. Dashboard rack cards (approximately lines 2558–2577) also sum devices only; dashboard face insights (approximately lines 2616–2633) use unique occupied slots and exclude vertical accessories, but read `rackFace` rather than the current `face` property. Rack overview (approximately lines 2885–2903) counts unique occupied slots, excludes vertical accessories and prefers `face` with a `rackFace` fallback. Individual rack workspace (approximately lines 2997–3008) sums device and horizontal accessory heights. `phase13LUsage()` (approximately lines 2825–2839) counts vertical accessory spans as numbered U; it supplies rack summary and print capacity (approximately lines 2850–2868), while printed slots exclude vertical accessories. These are source-confirmed discrepancies; browser effects are not yet verified. Investigate one shared read-only occupancy calculation with explicit face, unique-position and accessory rules, while preserving separate mutation validation and compatible historical records. Include dashboard cards, reports, Racks CSV, rack overview, individual rack workspace and print/PDF in one regression matrix. Do not duplicate this reporting scope under M-010/M-019, which address imported record integrity. No application change approved.

### M-025: Simplify Backup & Restore language and recovery controls

**Status:** Product direction approved by owner on 22 October 2026; implementation scope and release priority still require confirmation. No application changes made.

**Problem:** v1.3.0 Settings exposes both `Export Current Inventory` and `Download pre-restore snapshot`. The word *snapshot* is technical and the difference between the two downloads is not obvious to ordinary users. The product owner explicitly prefers a simple backup and restore experience while retaining automatic recovery safeguards.

**Approved user experience direction:**

- Present two primary actions in plain British English: **Back up your inventory** and **Restore an inventory**.
- Explain restore plainly: **Caffoot Lite automatically keeps a safety copy of your current inventory before replacing it.** Avoid the term *snapshot* in user-facing text.
- Keep the existing pre-restore safety-copy mechanism and verified save/rollback protection. Do not delete safety copies or merge them into the ordinary user-created backup.
- Make the optional recovery control discoverable but secondary, for example under **Recover previous inventory** or **Recovery options**, rather than presenting it as a competing primary backup action. Preserve a means to download the existing pre-restore copy. Do not promise one-click recovery or automatic restoration until the actual implementation is designed and tested.
- Do not remove existing backup export/import capabilities or alter backup file formats as part of this wording and layout change.

**Current v1.3.0 behaviour:** Settings `phase11SafetyPanelHTML()` labels the two actions `Export Current Inventory` and `Download pre-restore snapshot`; `phase11-export-backup` calls `exportData()`, and `phase11-download-snapshot` calls `phase11DownloadSnapshot()`. The ordinary export adds `caffootBackup` metadata; the safety-copy download exports the stored text unchanged. The technical workflow baseline must retain these actual names and behaviour.

**Implementation decision still open:** Confirm exact recovery wording, placement and whether recovery means download only or a separately designed restore flow. Do not silently add a destructive recovery action. Test that backup export, import, automatic safety copy, snapshot download, rollback, and recovery mode remain functional and accessible after the interface change. Update the user guide and relevant technical workflow docs alongside any future application change. Public-facing text must use British English and avoid hyphens as punctuation.

### Additional candidate: M-026 Shared form lifecycle and consistent editing safeguards

**Status:** Investigation required. Product owner has proposed making Save, Cancel and Edit behaviour consistent across forms wherever practical. This records the design direction for assessment, **not** approval to refactor application code or a commitment to the v1.3.1 release.

**Problem in plain English:** Users should not have to learn different rules for saving, cancelling or abandoning changes depending on which record they are editing. Developers should not have to recreate the same protections in every form. Current v1.3.0 source has multiple specialised submit handlers, explicit catalogue Save buttons, `closeModal(force)` and independently saved child records. Some nested cancellation paths bypass the standard dirty-form prompt, and some save paths have different rollback and feedback guarantees.

**Source evidence:** Published `v1.3.0` `app/caffoot-lite.html`: `openModal()`, `closeModal()`, `modalFormSnapshot()`, `phase120ConfirmDiscard()`, `handleDeviceSubmit()`, `handleSubnetSubmit()`, `handleRackSubmit()`, `handleIpSubmit()`, `handleAssignSubmit()`, `handleBulkIpSubmit()`, `phase12BApply()`, `phase120ManufacturerSave()`, `phase120ModelSave()`, `phase120SoftwareSaveCustom()` and `phase120SaveServerService()`. See WF-07 source audit and M-018/M-022; do not duplicate those defect candidates.

**Proposed approach for assessment:** Define a small common form lifecycle contract: open/edit from an unchanged saved record; track meaningful unsaved changes; validate using record-specific rules; apply a candidate change; persist and verify; on failure restore previous state and show a consistent error; on success close and restore focus; on cancel ask before discarding meaningful edits. Keep specialist business logic, IPAM/rack relationship checks, conversion confirmations, and deliberately independent saves in dedicated functions. Prefer shared helpers or conventions over one large generic Save function.

**Risks and dependencies:** An indiscriminate refactor could lose unsaved drafts, double-save records, change keyboard behaviour, break catalogue legacy values or make historical inventories impossible to save. Nested device-to-subnet/rack flows, bulk IP confirmation and automatic pre-restore safety copies require explicit exceptions and tests. Reconcile with M-004, M-007, M-018 and M-022 before prioritisation.

**Acceptance and regression checks:** Inventory all form families and their current save/cancel semantics; test new/edit, invalid input, unchanged form, modified cancel, Escape, Enter, failed storage write/readback, focus restoration, nested forms and independently saved child records. Verify existing inventories and older backups still load, edit and save without additional restrictions. Document any justified exceptions. Assess scope and release priority with the owner before coding.


### M-027: Return to editing from bulk IP confirmation

**Status:** Product owner supports adding a **Back to Editing** option (22 October 2026). User experience direction agreed; implementation and v1.3.1 inclusion are not yet authorised. Browser verification pending.

**Problem in plain English:** The bulk IP reservation/release form opens a separate confirmation view after Preview Changes. That view offers Cancel and Apply but no way to return to the completed form and correct the range, labels or action. Starting again is unnecessary friction, especially for larger changes.

**Published source evidence:** `app/caffoot-lite.html`, v1.3.0 blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`, `openBulkIpModal()` and `handleBulkIpSubmit()` around lines 4444–4492. `handleBulkIpSubmit()` replaces the form via `openModal()`, while `phase12BPending` retains the request values for `phase12BApply()`. The confirmation's Cancel closes the modal; no explicit Back/Edit action appears in this path. This is a source-supported usability improvement, not a browser-confirmed data loss defect.

**Agreed design direction:** Add **Back to Editing** to the confirmation. Restore the original First Host Offset, Last Host Offset, action, label prefix and notes without applying any changes. Keep **Cancel** as an explicit abandonment action and **Apply** as the only operation that commits the reviewed request. Recalculate the preview on the next Preview Changes action and preserve existing device-owned address protections, the pre-apply safety copy, save failure rollback and validation. Do not weaken IPAM safeguards or alter backup formats.

**Checks before implementation:** Confirm the existing behaviour in a disposable browser inventory. Then test Preview → Back → edit → Preview → Apply; repeated Back/Preview cycles; Cancel after preview; keyboard/focus return; narrow screens; protected addresses; zero-change previews; failed storage and recovery. ### M-031: Bulk IPAM safety snapshot readback before applying changes

**Status:** New source-supported investigation candidate. No browser reproduction, application change or release priority approved.

**Evidence:** Published v1.3.0 `phase12BApply()` in `app/caffoot-lite.html`, approximately lines 4493–4518, writes `caffoot_phase12b_prebulk_snapshot` with `localStorage.setItem()` inside a try/catch. It cancels if that call throws, but does not immediately read the snapshot back to confirm the expected bytes before modifying `appState.ipAllocations`. It subsequently calls `saveState()` and restores the prior in-memory state if saving returns false. In contrast, backup import and Clean Start explicitly check safety snapshot readback before replacing the inventory.

**Why it matters:** A storage write that silently fails may not throw, so the bulk operation could proceed without a verified safety copy. This is a **source-observed inconsistency**, not proof of data loss or a reproduced defect. The primary inventory save has its own readback verification; the safety copy serves a separate recovery purpose.

**Required investigation:** In a disposable browser profile with fictional data, simulate thrown and silently rejected safety snapshot writes, then failed and successful main inventory writes. Compare original and resulting saved bytes, in-memory allocations, safety snapshot contents, messages and reload behaviour. Decide whether immediate snapshot readback, stronger rollback reporting or another safeguard is appropriate. Review alongside M-012 and WF-12 without merging distinct operations into one finding.

**Approval boundary:** Record test results and seek product owner approval before changing code or including this work in a release.

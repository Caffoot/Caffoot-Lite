# Caffoot Lite v1.3.1 maintenance roadmap

**Status:** Proposed scope for product owner review, 23 October 2026. No new application change or release authorised.
**Published baseline:** v1.3.0. Some corrections are already merged into `main` but not included in the published v1.3.0 package.
**Full history:** [Preserved 601 line investigation register](V1.3.1-MAINTENANCE-INVESTIGATION-HISTORY.md).
**Tracking:** [Audit findings remediation programme](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md).

**Proposed release split:** v1.3.1 focuses on inventory safety, v1.3.2 on usability and editing consistency, and v1.3.3 on code clarity and remaining audit reconciliation. The [central remediation programme](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md#proposed-v13x-release-allocation-23-october-2026) records the full item allocation. This is planning only, not approval for changes or publication. M-030 documentation controls apply to every release.

**M-005 product decision, 23 October 2026:** Physical servers with dependent virtual servers cannot be deleted or converted until the virtual servers have been reassigned to another physical server or individually deleted. If necessary, users may create another physical server first. No automatic deletion or silent reassignment is permitted. This rule is agreed for design but not implemented or tested; legacy import compatibility remains open. See the [M-005 decision record](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md#m-005-product-owner-decision-23-october-2026).

**Hypervisor hosting design agreed, 23 October 2026:** A physical server's selected hypervisor product should control its Hypervisor service and eligibility as a virtual server host. Selecting a host should automatically determine the virtual server's platform. Existing relationships and older backups require non-destructive compatibility handling. This is a design agreement, not an implemented or tested change. See the [M-005 hypervisor design record](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md#m-005-hypervisor-eligibility-and-platform-design-agreement-23-october-2026).

**Agreed hypervisor change behaviour:** A confirmed change of a physical server's selected hypervisor updates the recorded platform of every assigned virtual server in the same save, with full rollback if saving fails. Removing hypervisor eligibility remains blocked while dependants exist. This is a planned metadata change, not a real VM migration. See the [M-005 decision](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md#m-005-hypervisor-change-propagation-decision-23-october-2026).

## Aim

Make the next maintenance release safer and clearer without disrupting existing inventories. Investigate the most important data integrity risks, carry forward already merged safeguards, and verify the actual release package. Do not tighten validation in a way that prevents older inventories from being saved.

## Release readiness

Before approving a v1.3.1 release:

1. Confirm the exact `main` revision, intended changes and compatibility with existing and historical inventories.
2. Approve the individual fixes and verify the relevant source behaviour, including failure and rollback paths.
3. Execute targeted regression tests and package checks; record the exact runs and results. Previous successful tests remain valid historical evidence but do not replace release verification.
4. Update the [living technical workflows](../workflows/TECHNICAL-WORKFLOWS.md), [function reference](../standards/FUNCTION-NAMING-AND-REFERENCE.md), test matrices, findings register, user guidance and release notes where affected.
5. Reconcile the [master audit](../audits/V1.3.0-DOCUMENTATION-COVERAGE-AUDIT.md), documentation indexes and outstanding P12 coverage. Do not equate administrative audit closure with complete workflow verification.
6. Obtain explicit product owner approval before merging application changes, tagging or publishing.

## Tape equipment and optional component relationships, 24 October 2026

**Agreed scope boundary:** Do not expand the v1.3.1 inventory integrity work into unrestricted nested inventory. Preserve existing Tape Drive records, historic device types and data throughout v1.3.x. An optional LTO generation field for tape drives and clear differentiation between drive and cartridge generations are agreed design requirements, with exact delivery version and catalogue validation still to be planned. A tape library may contain drives of differing generations. Do not infer full tape cartridge management.

**v1.4.0 design candidate:** Explore a limited reusable model for independently inventoried devices, optional one-level installed components and optional connected-device relationships. No recursive component nesting, compulsory links, automatic cascading deletion or separate rack allocation for internal components. Keep standalone rack mounted libraries as devices. This is a future design candidate, not authorised implementation or a committed v1.4.0 release feature. Preserve compatibility with existing inventory, backup and import records.

**Status:** Owner agreed the scope direction. No application tests or changes at this checkpoint. Detailed workflow, test matrix, findings, master audit and documentation index reconciliation remains open; do not claim those checks complete.

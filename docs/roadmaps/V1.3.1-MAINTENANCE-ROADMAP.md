# Caffoot Lite v1.3.1 maintenance roadmap

**Status:** Proposed scope for product owner review, 23 October 2026. No new application change or release authorised.
**Published baseline:** v1.3.0. Some corrections are already merged into `main` but not included in the published v1.3.0 package.
**Full history:** [Preserved 601 line investigation register](V1.3.1-MAINTENANCE-INVESTIGATION-HISTORY.md).
**Tracking:** [Audit findings remediation programme](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md).

## Aim

Make the next maintenance release safer and clearer without disrupting existing inventories. Investigate the most important data integrity risks, carry forward already merged safeguards, and verify the actual release package. Do not tighten validation in a way that prevents older inventories from being saved.

## Priority investigations proposed for v1.3.1

| Findings | Plain English issue | Decision needed before implementation |
| --- | --- | --- |
| M-005 | Deleting or changing a physical server can leave virtual servers pointing to an invalid host | Agree relationship protection and safe handling of older inventories |
| M-006 | Changing a device IP may leave inconsistent address ownership or notes | Reproduce, establish correct allocation and rollback behaviour |
| M-009 | A network device legitimately using a gateway may block an unrelated subnet edit | Agree gateway ownership and legacy handling |
| M-010, M-019 | Imported racks and accessories may contain overlapping or invalid placements | Agree safe detection and recovery without data loss |
| M-014 | Recovery reset may not explain an ignored storage write clearly | Agree wording and safety preserving response |
| M-017 | A readable but invalid saved inventory may produce unclear startup feedback | Explain failure without overwriting user data |
| M-024 | An IP reservation may point to a missing device | Decide whether to warn, repair or reject while preserving legacy records |
| M-028 | Archived software or service assignments may disappear from details while remaining stored | Confirm display behaviour and preserve history |
| M-030 | Documentation and version checks may not match the actual released package | Establish a reliable release documentation gate |
| M-004, M-022 | Some failed save paths need further rollback review | Reconcile existing test evidence before adding tests |

This is a **priority investigation list**, not a promise that all corrections will fit into v1.3.1. Each code change requires a separate product owner decision. Other original findings remain tracked in the [remediation programme](../audits/AUDIT-FINDINGS-REMEDIATION-PROGRAMME.md), including M-002, M-003, M-023 and broader usability and maintainability work.

## Release readiness

Before approving a v1.3.1 release:

1. Confirm the exact `main` revision, intended changes and compatibility with existing and historical inventories.
2. Approve the individual fixes and verify the relevant source behaviour, including failure and rollback paths.
3. Execute targeted regression tests and package checks; record the exact runs and results. Previous successful tests remain valid historical evidence but do not replace release verification.
4. Update the [living technical workflows](../workflows/TECHNICAL-WORKFLOWS.md), [function reference](../standards/FUNCTION-NAMING-AND-REFERENCE.md), test matrices, findings register, user guidance and release notes where affected.
5. Reconcile the [master audit](../audits/V1.3.0-DOCUMENTATION-COVERAGE-AUDIT.md), documentation indexes and outstanding P12 coverage. Do not equate administrative audit closure with complete workflow verification.
6. Obtain explicit product owner approval before merging application changes, tagging or publishing.

**Current checkpoint:** Documentation proposal only. No application tests executed as part of this roadmap rewrite; no new maintenance release published.

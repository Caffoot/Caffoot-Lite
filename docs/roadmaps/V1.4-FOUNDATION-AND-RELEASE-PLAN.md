# v1.4 documentation and repository foundation

**Status:** Approved planning direction. Release allocations remain provisional until scoped and accepted by the product owner. This document is not implementation or release approval.

## Purpose

Make v1.4 the active development line for the single Caffoot Lite product, while preserving published v1.3.3 and earlier history. The first integration branch is `release/v1.4.0`. Changes use the fewest practical short-lived PR branches, with owner approval before application behaviour changes, merges or releases.

## Lite rules

Reuse proven v1.3.3 HTML, CSS, JavaScript and workflows where technically sound. Keep the interface recognisable while improving usability, accessibility and consistent light/dark styling. Prefer the simplest justified backend, database and container layout. Installation must be exceptionally easy through Docker Compose or Portainer, ideally one application container and durable storage, without manual database administration. Raspberry Pi 5 8 GB ARM64 and AMD64 are acceptance targets, not unverified performance claims.

Preserve historical inventories, custom values, identities and older JSON backup compatibility. Require secure administrator enrolment, mandatory administrator MFA with recovery codes, backend-enforced permissions, secure sessions and HTTPS reverse-proxy guidance. **No verified recovery path, no release.** Persistent volumes, versioned database migrations, complete backups, tested restoration and documented upgrade/rollback safeguards are mandatory. Unattended updates are opt-in.

## Documentation authority and navigation

Use the **existing** documentation layout rather than creating duplicate trees:

- [Standards](../standards/README.md) are mandatory. Preserve the established [function naming reference](../standards/technical/FUNCTION-NAMING-AND-REFERENCE.md) and [technical documentation policy](../standards/technical/TECHNICAL-DOCUMENTATION-POLICY.md).
- [Workflows](../workflows/README.md) explain verified application behaviour and the v1.3.3 migration baseline.
- [Architecture](../architecture/README.md) records design decisions, proposals and implementation boundaries.
- [Testing](../testing/README.md) holds matrices and actual evidence; source inspection is not a passed test.
- [Audits](../audits/README.md) holds findings, the master audit and the [documentation relocation register](../audits/DOCUMENTATION-RELOCATION-REGISTER.md).
- [Releases](../releases/README.md) holds release requirements.
- [Archive](../archive/README.md) preserves historical release-specific documents and evidence.
- [Documentation home](../README.md) provides the overall index.

Every documentation directory must have a readable `README.md` explaining purpose, authoritative documents and links. Update its index when files change, then verify indexes again at release checkpoints. Preserve compatible links and source references. Do not silently overwrite older release evidence with new behaviour.

**Write once, use many:** the application repository is authoritative for product facts, guides and technical documentation. `Caffoot/Caffoot-Website` owns website layout and publishing, and should consume version-pinned shared content. Only website-specific copy and metadata warrant separate files; avoid competing guide copies or unnecessary automation.

## Historical v1.3.x archiving plan

1. Inventory v1.3.x release-specific roadmaps, preparation records and notes and classify which are truly superseded.
2. Preserve shared standards, current technical references, compatibility contracts, successful tests and audit evidence at their authoritative paths, labelled by version where appropriate.
3. Move only superseded release-specific material to `docs/archive/vX.Y.Z/` with per-directory `README.md` indexes, as required by the existing archive policy.
4. Inspect and update inbound links, Markdown anchors, contributor indexes, CI consumers and release packaging dependencies before each move. Keep necessary compatibility stubs.
5. Preserve published v1.3.3 ZIPs, tags, GitHub release assets and the standalone packaging inputs. Do not rewrite historical release notes.
6. Reconcile PR #50's 13 changed documentation paths against existing authoritative files before closing it, preserving unique decisions without duplication. Initial read-only review of six architectural documents confirms unique proposed identity, migration, storage and data-model detail; these are **not** disposable or automatically approved. See the reconciliation register below.

The active roadmap and indexes should describe the v1.4 direction while linking to preserved historical evidence. Archiving is a documentation change and does not invalidate successful application tests.

## Release and verification discipline

Follow Understand, Agree, Implement, Verify, Document, Reconcile, Approve and release. Before testing, check what changed and reuse valid passing evidence. Documentation-only changes need only justified documentation/link checks, not application regression runs. Record tests actually executed separately from proposed tests. Do not merge into `main`, publish, change protections or implement unapproved behaviour.

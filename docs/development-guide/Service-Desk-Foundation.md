# Service Desk Foundation

Batch 5.1 introduces one equipment-linked ticket model in schema 25 and applies the approved employee and technician access rules at the HTTPS boundary. Batch 5.2 connects the foundation to the **IT → Service Desk** queue, ticket details and file workflows. Employee screens, reporting, category administration, templates and notifications have their own later batches. [Batch 5.1](https://github.com/Caffoot/Caffoot-Lite/issues/420)

## Storage And Transactions

A ticket links to exactly one canonical Device, individually tracked IT Asset unit or quantity-tracked stock item. A stock unit linked to an existing Device uses the Device's identity. The migration stores the precise assignment or original issue and keeps it with the ticket. Ticket author and actor labels are saved with their identifiers so later account changes leave the attribution intelligible.

SQLite foreign keys preserve equipment and ticket relationships. Categories have stable identifiers and the recorded category label is kept with each ticket and change event. New tickets start Open, Medium and Unassigned. An explicit closure records its resolution note and event. A reopening links back to that closure and preserves the same ticket ID and all earlier attempts. The working-time value is reserved for the later reporting batch.

Attachments belong to messages. Their bytes live in SQLite, which lets Clean Start remove attachments within the same transaction as the rest of the operational data. The reset also requests secure deletion for the SQLite pages it frees. Backups retain the information they captured. The central reset event records the operation without adding ticket contents or identifiers. [Schema](../../backend/service_desk_schema.py) · [Reset writer](../../backend/reset_inventory.py)

## Permission And Request Boundaries

The existing effective **Service Desk** section supports Read and Edit. Ordinary-account grants start empty, including upgrades with historical IT Staff memberships. The existing roles and per-user overrides govern access to the technician scope. Technician ticket access also needs the equipment feature to be enabled and effective Read access to that section.

Employee access requires a live account and a linked active Staff record. Each query checks the stored assignment against the current Staff or Department identity. Staff joins and departures change membership without changing the ticket's stored assignment. For stock issues, the ledger balance for the issue must have stayed above zero since the ticket was created. This closes the privacy boundary at a full return even when a later correction adds an outstanding quantity back to the same issue. [Audience filter](../../backend/service_desk_access.py)

The HTTPS handler puts reads in a consistent database snapshot and locks writes before authorisation and changes. Read and mutation paths use the existing session and origin checks, and mutations require session-bound CSRF proof. Requests use the `/api/service-desk/` prefix with `personal`, `department` or `it` scopes. The same scope filter checks list results, counts, searches, ticket details, message and attachment resources, history and writes. Private fields have a separate history column, and attachment bytes inherit access from their parent message. ## IT Service Desk

`interface/service-desk.js` connects the frozen Design 01 layout to the existing application shell, Device Inventory toolbar and shared Device Details modal. The queue defaults to Open. Its status, priority, assignment, technician and search filters and its sort order execute against the authorised server scope. Workload counts stay independent of the filters. The Device Details **Tickets** tab and the Stock Item Details **Linked Tickets** section use the same query with a canonical equipment filter. Closing a ticket opened from Device Details restores the tab and its current page. A Stock Item Details panel can include its individually tracked non-Device units. Registered Devices retain their Device identity. The corresponding optional feature and section permission are required at each read. [Design 01](https://github.com/Caffoot/Caffoot-Lite/blob/2dbfbd8aebdcd7237845c7ea559f52548e5600de/future-design/stage-5-previews/01-service-desk-it.html) · [Integrated evidence](../development-handovers/evidence/it-service-desk/README.md)

The scoped equipment endpoint provides canonical choices for authorised creation. Current stock issues are identified individually when a stock item has multiple recipients. The ticket writer rechecks the selected issue and records the applicable assignment before saving the ticket. The technician selector and assignment operation share the same eligibility check. The browser submits the ticket’s last-updated time with classification and lifecycle actions so two technicians cannot silently apply conflicting actions from the same old view. Independent updates can both be appended.

Ticket creation and new IT updates accept an optional `attachments` list of filenames and base64 file contents. Original report files use a message in the verified employee audience. Files on subsequent updates inherit the message’s employee-visible flag, which defaults to internal for IT. The HTTP handler checks the session, origin, CSRF and current permission before reading a large request and checks permission again under the write lock. Validation checks names, decoded bytes and actual file structures. ZIP-based Office files are checked for the expected package and document type and bounded expansion. Attachments remain SQLite blobs. The message, files and event commit together, and the retained byte sum is checked under that lock.

Attachment access checks the ticket and its parent message before returning a non-cacheable, forced download. Removal uses the same edit scope and creates an attributed event with its parent message’s visibility. A removed file ID stays expired for that ticket when a new upload arrives. Ticket relations, attachment storage and Clean Start continue to use schema 25. ## Inventory Replacement And Clean Start

Normal Device deletion rejects a Device with protected ticket history. The existing legacy inventory writer retains a ticket-linked Device row in place when the reviewed candidate contains the same record. It can still replace unrelated inventory or change the Device's ordering. If a candidate would remove or replace a protected record, the import raises an error before writes. SQLite still enforces other existing inventory dependencies. Earlier schemas without a ticket table use their existing inventory replacement path.

Clean Start clears the operational data in Service Desk, inventory, IT Assets, equipment custody, Staff and Departments, Suppliers, Purchasing and Equipment Lifecycle. It restores the standard catalogues and lifecycle defaults. Accounts, authentication data, permission settings, Optional Features choices and central audit rows are retained. A linked account keeps its Staff identity and eligibility while its directory fields are returned to their starting values.

The existing authorised writer takes a single SQLite write lock. It defers foreign-key checks for the cycles between stock movements and assignments, removes dependent records and restores the targeted deletion guards before checking relationships and committing. A failure rolls back the data and the guards. The central audit entry records the reset without private ticket content. Old audit rows remain available under the established permissions. Readers without Devices access cannot use a new stock movement with a reused ID to reveal an older Device movement.

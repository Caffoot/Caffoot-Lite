## Cross-cutting questions before approval

1. Does every state mutation check `saveState()` and roll back in-memory changes when it returns false?
2. Does import validation enforce all invariants enforced by normal editing, including accessory occupancy and virtual host references?
3. Are all browser storage keys, migrations, snapshots, audit records and preference keys documented with retention and backup inclusion?
4. Are user confirmation, Escape, cancel and unsaved-change protections consistent across forms?
5. Are report and dashboard values derived consistently from the same inventory and filters?
6. Are built-in versus user-defined catalogue entries, archive behaviour and historical details fully explained?
7. Are packaging, offline dependencies, licence notices and exact release artifacts tested and documented?
8. Has the documentation been compared against the released HTML, other repository source, tests, build scripts and assets, not only a function list?

### WF-01 second pass, initial findings

**Source:** `app/caffoot-lite.html` on `main`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`, approximately lines 1615 to 1700. This is not yet proof of the exact published release source.

- Confirmed from source: absent storage returns default inventory without an immediate write; failed reads and malformed or unsafe saved JSON activate recovery mode; the original readable raw text is retained for download where available; saves are blocked while recovery mode is active.
- Confirmed distinction: readable, normalised inventory with integrity errors logs startup errors but does not automatically activate the same recovery mode. `saveState()` later blocks invalid saves.
- Reset requires two native browser confirmations and writes defaults before reloading. This reset handler does not explicitly verify the write by reading it back; browser failure testing remains outstanding.
- Follow-up: trace exactly when the recovery banner is mounted, startup UI behaviour, malformed-but-readable inventory, migration effects, reset failure, browser storage denial and all relevant tests.

**WF-01 review status:** Source reinspection started; documentation reconciliation partial; roadmap discussion pending; browser and automated evidence pending; not approved as complete.


### WF-01 second-pass continuation

Source inspection confirms that `window.onload` opens the dashboard then mounts the recovery banner, and that recovery mode may show default in-memory inventory while the original stored inventory remains untouched. The audit trail is stored separately, limited to 200 entries, and its failure does not invalidate a successful inventory write. Audit history is a compact summary and is not included in normal inventory backups. Add browser checks for user comprehension of the recovery screen, reset failure, and damaged audit storage. **WF-01 remains open.**

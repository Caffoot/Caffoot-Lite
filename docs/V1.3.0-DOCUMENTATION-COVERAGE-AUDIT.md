1. Does every state mutation check `saveState()` and roll back in-memory changes when it returns false?
2. Does import validation enforce all invariants enforced by normal editing, including accessory occupancy and virtual host references?
3. Are all browser storage keys, migrations, snapshots, audit records and preference keys documented with retention and backup inclusion?
4. Are user confirmation, Escape, cancel and unsaved-change protections consistent across forms?
5. Are report and dashboard values derived consistently from the same inventory and filters?
6. Are built-in versus user-defined catalogue entries, archive behaviour and historical details fully explained?
7. Are packaging, offline dependencies, licence notices and exact release artifacts tested and documented?
8. Has the documentation been compared against the released HTML, other repository source, tests, build scripts and assets, not only a function list?

## WF-01 to WF-02 boundary: verified save and audit sequence, 22 October 2026

Inspected published tag `v1.3.0` in `app/caffoot-lite.html`, functions `saveState()`, `recordAudit()` and `readAuditHistory()`. On a normal save, recovery mode blocks writes; `validateApplicationState()` blocks inconsistent inventory; `saveState()` serialises the inventory, writes `caffoot_state` and checks that reading it back produces identical text. Only after successful main-inventory verification does it attempt `recordAudit()`. Audit records use the separate `caffoot_audit_v1` key and are capped at 200 summary events. A failed audit-history write displays an error toast advising backup, but does not reverse the already verified inventory save. The history export is separate from the normal inventory backup. This is source inspection, not execution of failure injection or browser tests.

**WF-02 implications:** Catalogue all save callers and their in-memory rollback behaviour, and distinguish inventory persistence from auxiliary keys and best-effort audit history. A successful inventory write and matching readback are not an atomic multi-key transaction. Review secondary snapshots and failure outcomes separately.

**M-016 evidence:** Published GitHub release v1.3.0 is dated 21 October 2026, while `RELEASE-NOTES-1.3.0.md` at the published tag still says 'Draft release notes' and 'Release date: To be confirmed'. The document also contains historical pre-release validation notes. Preserve that historical context; plan a reviewed, narrowly scoped documentation reconciliation after asset verification. No release notes have been changed in this audit.

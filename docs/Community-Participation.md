# Caffoot Lite — Community Participation And Issue Labels

Caffoot Lite is for people who use it, document it, test it and build it. **You do not need to know how to code to help.** Everyone is welcome to report a problem, explain something confusing, suggest an idea or help somebody else get started.

## Where To Start

- [Open An Issue](https://github.com/Caffoot/Caffoot-Lite/issues/new/choose) to report a problem, suggest a feature, improve a guide or ask a question.
- [Read The Feature Guides](How%20To's/Features%20and%20Instructions/README.md) and tell us what could be clearer.
- [Explore Good First Issues](https://github.com/Caffoot/Caffoot-Lite/labels/good%20first%20issue) for approachable tasks identified by maintainers.
- [Explore Help Wanted Issues](https://github.com/Caffoot/Caffoot-Lite/labels/help%20wanted) for work where maintainers have asked for help.
- [Read CONTRIBUTING.md](../CONTRIBUTING.md) before proposing code or documentation changes.

If no beginner-friendly tasks are listed yet, that simply means none have been prepared; you're still welcome to suggest improvements or help test the application.

## What The Issue Labels Mean

These initial categories use GitHub's standard label names, where available. Repository maintainers should verify the label names under **Issues > Labels** before activating the forms. A label helps organise a request; it does not imply that the feature or fix has been approved.

| Label | Meaning | Who Applies It |
| --- | --- | --- |
| `bug` | Something does not work as expected | Automatically from Report A Bug |
| `enhancement` | A feature request or improvement idea | Automatically from Suggest A Feature |
| `documentation` | Clearer guides, screenshots, examples or code explanations | Automatically from Improve Documentation |
| `question` | A request for help or clarification | Automatically from Ask A Question |
| `good first issue` | A clearly scoped, approachable task for first-time contributors | Maintainers after review |
| `help wanted` | A task with agreed scope where community contributions are welcomed | Maintainers after review |
| `duplicate` | A request already being tracked elsewhere | Maintainers after review |

**Optional later label:** `UI / UX` could highlight interface and accessibility suggestions if that additional label is created and maintained. It is not required for the initial issue forms; interface suggestions can start as an `enhancement`.

## Simple Review Process

1. Thank the contributor and check whether the report is clear.
2. Use the appropriate label and ask for details politely when needed.
3. Confirm a bug before promising a fix. If the report may reveal a security weakness, stop public technical discussion and follow [Security Reporting](../SECURITY.md).
4. Keep ideas separate from approved development. [Future Ideas Register #222](https://github.com/Caffoot/Caffoot-Lite/issues/222) records the product owner's vision, not a blanket authorisation to implement suggestions.
5. Only mark an issue `good first issue` or `help wanted` once its scope and expected outcome are agreed and an external contributor could act on it.
6. If somebody wants to contribute, help them find the [Development Guide](Development%20Guide/README.md), source-code naming rules, clear British English comment standards and required documentation.
7. Before merging a pull request, apply the same tests, readability and documentation checks to maintainers and community contributors.

Be welcoming, patient and direct. A first-time contributor should never have to understand the entire codebase to report a spelling error or describe a problem they encountered.

## Private Information And Security Reports

Never post passwords, session cookies, authenticator secrets, API tokens, private network details, unredacted logs or personal data in an issue. [Read the Security Reporting Guide](../SECURITY.md) before sharing a possible vulnerability.

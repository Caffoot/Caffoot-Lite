# Caffoot Lite v1.3.1 Maintenance Roadmap

**Status:** Candidate investigation register. No v1.3.1 changes approved or implemented.
**Baseline:** Published v1.3.0, pending exact release commit verification.
**Purpose:** Capture potential defects, missing safeguards and maintenance improvements found while documenting the actual v1.3.0 application. This document does not assert that any candidate is a confirmed defect.

## Rules

- Preserve an accurate description of v1.3.0 in `TECHNICAL-WORKFLOWS.md`; do not silently rewrite historical behaviour.
- Record source evidence, reproduction steps, risk, dependencies and test requirements before confirming an issue.
- Distinguish **Investigation required**, **Confirmed issue**, **Approved for v1.3.1**, **Fixed and verified**, and **Closed without change**.
- Prioritisation and inclusion in v1.3.1 require product owner approval. No application code changes are authorised by this roadmap.
- Keep the published v1.3.0 application untouched unless separate maintenance work is explicitly approved.
- Use British English in public-facing text.

### Additional candidate: M-009 Gateway ownership and subnet editing

**Status:** Investigation required, source-supported scenario, runtime reproduction pending.

The device primary IP helper permits a gateway address on Firewall, Router and Layer 3 Switch devices, while the subnet form rejects any proposed gateway already recorded as a device primary IP or IPAM allocation, including when the gateway value is unchanged. Test whether editing an unrelated subnet field fails when its gateway is legitimately device-owned. Decide and document gateway ownership rules before approving a fix; preserve existing data and add regression tests.

**M-009 additional source evidence:** `phase10GatewaySubnet()` identifies a gateway directly from the subnet record, and `phase10SubnetSummary()` counts an unallocated gateway as reserved without storing an IPAM allocation. `setDevicePrimaryIp()` permits eligible network devices to own a gateway and creates a device-linked allocation. The subnet editor nevertheless rejects any proposed gateway already device-owned or present in IPAM, even when unchanged. Verify via browser testing after documentation; consider legacy and imported inventories before approving behaviour changes.

**M-005 import evidence:** `normaliseState()` and `validateApplicationState()`, both used during backup import, have no explicit `virtualHostId` relationship validation. Test an imported virtual server referring to a missing or no-longer-physical host. Determine desired rejection, warning or controlled recovery behaviour before implementing anything.

**M-009 import evidence:** Imported network gateways are checked for validity and membership in their subnet, but the shared integrity validator does not explicitly enforce permitted device types for a device owning that gateway. Test gateway ownership across imported legacy inventories and manual edits before agreeing one consistent policy.

### M-010: Consistent rack occupancy validation during import

**Status:** Source-supported candidate; browser reproduction and design approval pending.

**Evidence:** The normal rack editing and movement paths use `validateRackPlacement()` and `phase13CAccessoryError()`, but backup normalisation and `validateApplicationState()` do not perform equivalent pairwise device or accessory occupancy checks. Imported accessory records are not comprehensively validated for rack reference, face, bounds and collisions. See WF-05/WF-06 cross-workflow finding in `docs/TECHNICAL-WORKFLOWS.md`.

**Proposed investigation:** Construct disposable backups with two devices on the same rack face and U, overlapping normal accessories, out-of-bounds accessories and invalid 0U rail placements. Check whether import accepts them, whether data remains readable, and whether existing inventory is preserved on rejection. Agree a shared validation policy that respects front/rear separation, legitimate side rails and historic backup compatibility. Do not silently delete or relocate equipment.

**No fix authorised.**

### M-011: Verify secondary snapshot restoration during failed import rollback

**Status:** Source-supported verification candidate; no fix approved.

**Evidence:** `importData()` verifies the original inventory string after rollback, but does not separately read back the previous `caffoot_phase11_pre_restore` snapshot after restoring or removing it. Source: `app/caffoot-lite.html`, approximately lines 7815–7850.

**Investigation:** In a disposable browser profile, simulate a failed candidate save, failed rollback write and a storage implementation that does not persist a previous-snapshot restoration as expected. Confirm original inventory protection, recovery mode, snapshot availability and audit consistency. Avoid asserting data loss without reproduction. Preserve the existing fail-closed restore behaviour.


### M-012: Integrity repair snapshot verification and failed-save recovery

**Status:** Investigation required. Source observation only; no reproduced data loss or approved fix.

**Evidence:** `phase11CApplyRepair()` stores `caffoot_phase11c_pre_repair_v1` before mutating IPAM but does not explicitly compare a readback of that snapshot. If a subsequent operation throws or `saveState()` reports failure, the handler restores the prior in-memory inventory and attempts to reinstate the previous snapshot, silently ignoring an error in that reinstatement. This catch path does not independently verify the main inventory storage or snapshot. `saveState()` separately validates and checks exact main-inventory readback on its success path.

**Next step:** Test in a disposable browser profile with storage failures before and after snapshot writes and during the main inventory save. Establish whether the existing safeguards are sufficient, what remains recoverable and whether snapshot readback or additional failure reporting would improve protection. Preserve compatibility and seek approval before any change.


### M-013: Include rack accessories in occupancy reporting

**Status:** Product owner suggested improvement; requirements and implementation not yet approved.

**Current v1.3.0 source behaviour:** `phase10DReportData()` calculates front and rear rack occupancy by summing mounted device U ranges only. Rack accessories are not included in the report's occupancy calculation. Source: `app/caffoot-lite.html`, `main`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`.

**Proposed behaviour for review:** Count horizontal rack accessories that consume U positions, alongside devices, on the relevant face. Track vertical or side-mounted accessories separately without treating them as horizontal U consumption. Calculate occupied positions as a union of valid occupied U slots per face rather than summing heights, to avoid double counting. Retain clear front and rear totals and agree whether a single overall rack percentage should represent maximum face occupancy. Do not assume every accessory consumes U space; inspect actual accessory types and placement schema first.

**Investigation and tests:** Trace accessory records, rack placement and face semantics; compare rack graphics and free-space calculations; test mixed devices and accessories, overlapping or imported legacy records, front/rear separation, side rails, and empty racks. Confirm the intended capacity definition with the product owner before implementation. Update report UI, CSV, tests and technical workflows together if approved. No application changes authorised.


### M-014: Recovery reset write verification

**Status:** Source-supported investigation candidate; no confirmed defect or approved change.

**Evidence:** The recovery banner's reset handler requires two confirmations and calls `localStorage.setItem('caffoot_state', ...)` before reloading, but does not explicitly compare a readback, unlike `saveState()`. A thrown error is displayed. Test in a disposable profile whether this distinction has any practical impact and whether adding verification would improve consistency.

### M-015: Visibility of automatic legacy inventory normalisation

**Status:** Proposed usability and data transparency improvement for product owner discussion; not approved.

**Evidence:** `normaliseState()` can update retired location values, managed type/location lists and device-owned IPAM links in the in-memory inventory during startup. The startup path does not immediately write the normalised inventory to storage or present a dedicated change summary. Consider a non-destructive notice or preview that explains meaningful corrections, without introducing automatic overwrite or disrupting legacy backup compatibility. First verify exact migrations, which cases are expected, and user impact.


**M-015 product owner design direction, 22 October 2026:** Prefer a small, non-intrusive notice when startup normalisation makes meaningful corrections to an older inventory, with a way to review what changed before saving. Preserve the original stored inventory until the user explicitly saves through the normal validated path. This is agreement on the desired experience, not authorisation to implement, a release commitment or proof that all normalisation changes can currently be detected. Investigate how to distinguish material corrections from routine default filling and how to avoid alarming users unnecessarily.

### Owner decision on M-014 — 22 October 2026

**Agreed in principle:** Strengthen the emergency recovery-banner reset by verifying that the replacement empty inventory was actually retained in browser storage before reloading. This decision approves the improvement as future work only. It does **not** authorise implementation, determine the release version or timing, or permit changes to the released application. Preserve the two explicit confirmations and the option to download readable original data. Design and test blocked writes, silently unsuccessful writes, readback failures and continued recovery without risking the original data. Review the implementation separately before any code change.


### M-017: Explain startup integrity problems to users

**Status:** Proposal for owner discussion, not approved implementation.

**Evidence:** On startup, a readable inventory that fails `validateApplicationState()` produces a developer-console error, but does not activate the visible unreadable-inventory recovery banner. A later attempted save is blocked with a visible message. Consider a non-destructive, clearly worded startup notice that explains the inventory is visible but cannot be safely saved until the reported issues are resolved, and provides guidance on backing up data. Avoid presenting a recoverable integrity issue as an erased inventory. Verify in browser and design the recovery journey before approval.

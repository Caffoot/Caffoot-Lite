# Caffoot Lite v1.3.1 Maintenance Roadmap

**Status:** Candidate investigation register. No v1.3.1 changes approved or implemented.
**Baseline:** Published v1.3.0 HTML at tag `v1.3.0`, commit `92d6a60b0e4bc9f73589b27820cb283def377dbd`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`. Other packaged assets and runtime tests remain separate checks.
**Purpose:** Capture potential defects, missing safeguards and maintenance improvements found while documenting the actual v1.3.0 application. This document does not assert that any candidate is a confirmed defect.

## Rules

- Preserve an accurate description of v1.3.0 in `TECHNICAL-WORKFLOWS.md`; do not silently rewrite historical behaviour.
- Record source evidence, reproduction steps, risk, dependencies and test requirements before confirming an issue.
- Distinguish **Investigation required**, **Confirmed issue**, **Approved for v1.3.1**, **Fixed and verified**, and **Closed without change**.
- Prioritisation and inclusion in v1.3.1 require product owner approval. No application code changes are authorised by this roadmap.
- Keep the published v1.3.0 application untouched unless separate maintenance work is explicitly approved.
- Use British English in public-facing text.

### Additional candidate: M-009 Gateway ownership and subnet editing

**Status:** Investigation required, source-supported scenario, runtime reproduction pending.

The device primary IP helper permits a gateway address on Firewall, Router and Layer 3 Switch devices, while the subnet form rejects any proposed gateway already recorded as a device primary IP or IPAM allocation, including when the gateway value is unchanged. Test whether editing an unrelated subnet field fails when its gateway is legitimately device-owned. Decide and document gateway ownership rules before approving a fix; preserve existing data and add regression tests.

**M-009 additional source evidence:** `phase10GatewaySubnet()` identifies a gateway directly from the subnet record, and `phase10SubnetSummary()` counts an unallocated gateway as reserved without storing an IPAM allocation. `setDevicePrimaryIp()` permits eligible network devices to own a gateway and creates a device-linked allocation. The subnet editor nevertheless rejects any proposed gateway already device-owned or present in IPAM, even when unchanged. Verify via browser testing after documentation; consider legacy and imported inventories before approving behaviour changes.

**M-005 import evidence:** `normaliseState()` and `validateApplicationState()`, both used during backup import, have no explicit `virtualHostId` relationship validation. Test an imported virtual server referring to a missing or no-longer-physical host. Determine desired rejection, warning or controlled recovery behaviour before implementing anything.

**M-009 import evidence:** Imported network gateways are checked for validity and membership in their subnet, but the shared integrity validator does not explicitly enforce permitted device types for a device owning that gateway. Test gateway ownership across imported legacy inventories and manual edits before agreeing one consistent policy.

### M-010: Consistent rack occupancy validation during import

**Status:** Source-supported candidate; browser reproduction and design approval pending.

**Evidence:** The normal rack editing and movement paths use `validateRackPlacement()` and `phase13CAccessoryError()`, but backup normalisation and `validateApplicationState()` do not perform equivalent pairwise device or accessory occupancy checks. Imported accessory records are not comprehensively validated for rack reference, face, bounds and collisions. See WF-05/WF-06 cross-workflow finding in `docs/TECHNICAL-WORKFLOWS.md`.

**Proposed investigation:** Construct disposable backups with two devices on the same rack face and U, overlapping normal accessories, out-of-bounds accessories and invalid 0U rail placements. Check whether import accepts them, whether data remains readable, and whether existing inventory is preserved on rejection. Agree a shared validation policy that respects front/rear separation, legitimate side rails and historic backup compatibility. Do not silently delete or relocate equipment.

**No fix authorised.**

### M-011: Verify secondary snapshot restoration during failed import rollback

**Status:** Source-supported verification candidate; no fix approved.

**Evidence:** `importData()` verifies the original inventory string after rollback, but does not separately read back the previous `caffoot_phase11_pre_restore` snapshot after restoring or removing it. Source: `app/caffoot-lite.html`, approximately lines 7815–7850.

**Investigation:** In a disposable browser profile, simulate a failed candidate save, failed rollback write and a storage implementation that does not persist a previous-snapshot restoration as expected. Confirm original inventory protection, recovery mode, snapshot availability and audit consistency. Avoid asserting data loss without reproduction. Preserve the existing fail-closed restore behaviour.


### M-012: Integrity repair snapshot verification and failed-save recovery

**Status:** Investigation required. Source observation only; no reproduced data loss or approved fix.

**Evidence:** `phase11CApplyRepair()` stores `caffoot_phase11c_pre_repair_v1` before mutating IPAM but does not explicitly compare a readback of that snapshot. If a subsequent operation throws or `saveState()` reports failure, the handler restores the prior in-memory inventory and attempts to reinstate the previous snapshot, silently ignoring an error in that reinstatement. This catch path does not independently verify the main inventory storage or snapshot. `saveState()` separately validates and checks exact main-inventory readback on its success path.

**Next step:** Test in a disposable browser profile with storage failures before and after snapshot writes and during the main inventory save. Establish whether the existing safeguards are sufficient, what remains recoverable and whether snapshot readback or additional failure reporting would improve protection. Preserve compatibility and seek approval before any change.


### M-013: Include rack accessories in occupancy reporting

**Status:** Product owner suggested improvement; requirements and implementation not yet approved.

**Current v1.3.0 source behaviour:** `phase10DReportData()` calculates front and rear rack occupancy by summing mounted device U ranges only. Rack accessories are not included in the report's occupancy calculation. Source: `app/caffoot-lite.html`, `main`, blob `e8a24f6370a1bb572287aad91a314a3e4a189d94`.

**Proposed behaviour for review:** Count horizontal rack accessories that consume U positions, alongside devices, on the relevant face. Track vertical or side-mounted accessories separately without treating them as horizontal U consumption. Calculate occupied positions as a union of valid occupied U slots per face rather than summing heights, to avoid double counting. Retain clear front and rear totals and agree whether a single overall rack percentage should represent maximum face occupancy. Do not assume every accessory consumes U space; inspect actual accessory types and placement schema first.

**Investigation and tests:** Trace accessory records, rack placement and face semantics; compare rack graphics and free-space calculations; test mixed devices and accessories, overlapping or imported legacy records, front/rear separation, side rails, and empty racks. Confirm the intended capacity definition with the product owner before implementation. Update report UI, CSV, tests and technical workflows together if approved. No application changes authorised.


**Additional WF-05 source evidence, 22 October 2026:** Published v1.3.0 `phase10DReportData()` (approximately lines 2305–2336) supplies both the Reports view and the Racks CSV. It sums device U heights by `face`, omits horizontal accessories and can double count overlapping imported records. The maximum of front/rear counts defines the report percentage and should not be changed without an explicit product decision. Dashboard rack cards (approximately lines 2558–2577) also sum devices only; dashboard face insights (approximately lines 2616–2633) use unique occupied slots and exclude vertical accessories, but read `rackFace` rather than the current `face` property. Rack overview (approximately lines 2885–2903) counts unique occupied slots, excludes vertical accessories and prefers `face` with a `rackFace` fallback. Individual rack workspace (approximately lines 2997–3008) sums device and horizontal accessory heights. `phase13LUsage()` (approximately lines 2825–2839) counts vertical accessory spans as numbered U; it supplies rack summary and print capacity (approximately lines 2850–2868), while printed slots exclude vertical accessories. These are source-confirmed discrepancies; browser effects are not yet verified. Investigate one shared read-only occupancy calculation with explicit face, unique-position and accessory rules, while preserving separate mutation validation and compatible historical records. Include dashboard cards, reports, Racks CSV, rack overview, individual rack workspace and print/PDF in one regression matrix. Do not duplicate this reporting scope under M-010/M-019, which address imported record integrity. No application change approved.

### M-014: Recovery reset write verification

**Status:** Source-supported investigation candidate; no confirmed defect or approved change.

**Evidence:** The recovery banner's reset handler requires two confirmations and calls `localStorage.setItem('caffoot_state', ...)` before reloading, but does not explicitly compare a readback, unlike `saveState()`. ### M-015: Visibility of automatic legacy inventory normalisation

**Status:** Proposed usability and data transparency improvement for product owner discussion; not approved.

**Evidence:** `normaliseState()` can update retired location values, managed type/location lists and device-owned IPAM links in the in-memory inventory during startup. The startup path does not immediately write the normalised inventory to storage or present a dedicated change summary. Consider a non-destructive notice or preview that explains meaningful corrections, without introducing automatic overwrite or disrupting legacy backup compatibility. First verify exact migrations, which cases are expected, and user impact.


**M-015 product owner design direction, 22 October 2026:** Prefer a small, non-intrusive notice when startup normalisation makes meaningful corrections to an older inventory, with a way to review what changed before saving. Preserve the original stored inventory until the user explicitly saves through the normal validated path. This is agreement on the desired experience, not authorisation to implement, a release commitment or proof that all normalisation changes can currently be detected. Investigate how to distinguish material corrections from routine default filling and how to avoid alarming users unnecessarily.

### M-017: Explain startup integrity problems to users

**Status:** Product owner agreed in principle on 22 October 2026. Design, browser verification, release allocation and implementation remain unapproved.

**Evidence:** On startup, a readable inventory that fails `validateApplicationState()` produces a developer-console error, but does not activate the visible unreadable-inventory recovery banner. A later attempted save is blocked with a visible message. Consider a non-destructive, clearly worded startup notice that explains the inventory is visible but cannot be safely saved until the reported issues are resolved, and provides guidance on backing up data. Avoid presenting a recoverable integrity issue as an erased inventory. Verify in browser and design the recovery journey before approval.


**M-017 product owner decision, 22 October 2026:** Agreed in principle to provide a clear, friendly, non-intrusive notice when readable inventory fails startup integrity validation. The notice should explain that the inventory remains visible but saving is blocked until the issue is resolved, provide a way to review the problem and guide the user towards protecting their original data. Do not silently delete, reset, overwrite or automatically repair questionable data. Preserve the existing save validation safeguards. This is design direction only, not approval to implement or a commitment to v1.3.1. Browser reproduction, failure handling, wording, test coverage and exact recovery journey require separate review.


### M-018: Custom location creation must report failed saves accurately

**Status:** Source-supported investigation candidate; browser reproduction and owner design approval pending. No implementation authorised.

**Evidence:** In the published v1.3.0 source, `addCustomLocationOption()` adds a new location to the device form and, if absent, pushes it into `appState.deviceLocations`, then calls `saveState()` without checking the boolean result. The function subsequently displays `Added location: ...` regardless of save success. If the write is rejected, the in-memory list and visible form option may differ from persisted inventory. Source: `app/caffoot-lite.html`, tag `v1.3.0`, approximately lines 7020–7040.

**Investigation:** In a disposable browser profile, add a fictional location with normal storage, then inject a failed inventory write or an integrity validation failure. Check success messaging, in-memory managed options, device form selection, reopening the form and behaviour after reload. Determine whether the form option should remain available as an unsaved draft or be rolled back; preserve entered device details. Compare all other catalogue and managed-list mutations for the same pattern. Do not classify as a reproduced defect or schedule a fix without evidence and approval.


### M-019: Imported rack accessory integrity coverage

**Status:** Source confirmed validation coverage gap; browser reproduction and solution design pending. Published v1.3.0 `validateApplicationState()` (approximately lines 1556–1616) validates device rack references and range consistency but does not iterate over `rackAccessories` or check device/accessory or accessory/accessory overlaps. `phase16CCheckBackup()` relies on this validator after migration. Normal interactive accessory placement uses `phase13CAccessoryError()` with stronger collision checks. Investigate validation for imported accessory rack references, bounds, face/side, horizontal occupancy and vertical rail collisions, and device/device overlaps as a related question. Preserve non-destructive import rejection and existing recovery safeguards. Build adversarial import fixtures and execute browser tests before deciding implementation. No code change authorised.


**M-019 migration follow-up (22 October 2026):** `phase20MigrateBackup()` clones the raw backup, applies limited legacy device mounting repairs and calls `normaliseState()`. `normaliseState()` carries over `rackAccessories` arrays unchanged, or supplies an empty array when absent; it does not validate individual accessory placement. The subsequent `validateApplicationState()` also lacks accessory checks. This strengthens the source-level coverage finding. Proposed design discussion: centralise shared rack occupancy validation for interactive edits, import and startup integrity checks; avoid automatic movement or deletion of user accessories. Include an explicit decision on malformed accessory collection types (currently normalised to empty) and test non-destructive rejection and recovery. No tests run and no code change approved.

### M-020: Device graphic save result not checked

**Status:** Investigation required. Source-supported candidate, not a browser-confirmed defect.

**Evidence:** Published v1.3.0 `phase13GSaveGraphics()` at HTML lines 2815–2821 updates `appState.deviceTypeGraphics`, calls `saveState()` without checking the Boolean result, then opens the management modal and refreshes the page. If storage rejects the save, the new graphic may remain in memory despite not being persisted. The interface also refreshes after failure, potentially confusing the user. This is a display preference rather than a rack placement change.

**Investigation:** With fictional data and isolated storage failure, inspect the graphic choice, error notification, screen after refresh, stored inventory and reload result. Decide whether snapshot rollback and a stopped UI transition are warranted. Cross-reference `WF-01-TO-WF-04-FUNCTION-AND-COMMENT-RECONCILIATION.md`, WF-02 scenario S28 and future WF-08 tests. No code change authorised.

### M-022: Rack selection after failed new rack save

**Status:** Investigation required. Source-supported candidate, not a browser-confirmed defect.

**Evidence:** In the published v1.3.0 rack creation/edit handler (HTML lines 5469–5477), the new rack is added and `selectedRackId` is set to its identifier before calling `saveState()`. On failure, `appState` is restored from `before`, but `selectedRackId` is not explicitly restored. The inventory rollback is present; the potential issue concerns auxiliary interface selection.

**Investigation:** In a disposable browser profile, simulate failed storage while creating a rack. Confirm the inventory remains unchanged, inspect the selected rack, modal and subsequent navigation, and check that no phantom rack is displayed or referenced. If there is a user-visible issue, consider restoring the previous selection as part of the already established rollback path. Reuse the existing WF-02 failure-injection fixture and WF-05 rack regression cases. No change approved.

### M-023: Rack accessory failure feedback and retry experience

**Status:** Investigation required. Source-supported UX candidate; browser testing pending.

**Evidence:** In published v1.3.0 HTML, the rack accessory form submit handler (lines 8103–8115) restores the inventory and returns when `saveState()` fails, without an additional handler-level error message. The delete confirmation handler (lines 8133–8138) removes the confirmation overlay before saving; if the save fails, it restores inventory but does not reopen the overlay or explicitly rerender the view. The shared `saveState()` may itself show a failure notification, so do not assert the user receives no feedback without testing.

**Investigation:** Use disposable rack accessories and simulated failed storage. Confirm the shared save notification, whether the form or confirmation state is clear, whether the displayed accessory matches restored inventory and whether retry works. Keep any proposed changes modest and consistent with existing form behaviour. Reuse WF-02 and WF-05 scenarios. No fix approved.

**M-023 clarification, 22 October 2026:** `saveState()` already shows an error toast when recovery mode blocks saving, validation rejects inventory or browser storage fails (published HTML lines 1825–1853). Therefore do **not** characterise accessory failures as silent solely because the accessory handler does not show a second toast. M-023 is specifically about whether the accessory form or already-dismissed deletion confirmation offers clear retry and consistent visible state after rollback. Test the shared notification and UI together before deciding on changes.

# Next — verified v1.3.3 compatibility investigation

**Status:** Technical evidence and open checks only. **No implementation authorised.**
**Sole Next scope/acceptance authority:** [Issue #215](https://github.com/Caffoot/Caffoot-Lite/issues/215).
**Behavioural baseline:** [Published v1.3.3 application](https://github.com/Caffoot/Caffoot-Lite/blob/v1.3.3/app/caffoot-lite.html).
**Working branch:** `Next`. If this reference conflicts with #215 or the published source, correct this reference; never infer approval from it.

## 1. Scope boundary

Next replaces authoritative browser inventory storage with a backend and central SQLite database, deployed simply via Docker Compose/Portainer. Only #215's approved accounts, MFA, RBAC, first-run setup and simultaneous device edit-reservation behaviour may be added. Existing Devices, IPAM and Racks functionality, appearance, terminology, validations and outcomes remain those of published v1.3.3.

No new inventory features, device-type change workflow, ticketing, public registration, UI redesign or unapproved repair flows. Do not reproduce browser safety snapshots/recovery banners or ongoing in-app JSON export: #215 deliberately replaces those storage-specific mechanisms. Legacy JSON **import** remains for fresh backups exported from published v1.3.3 only, with applicable validation/review/confirmation. Users on older HTML releases must first upgrade to v1.3.3, check their inventory, and export a new JSON backup. Direct schema-0/schema-1 import is no longer required by revised #215. No implementation, new tests, merge or release is authorised by this document.

## 2. Verified published-source inventory and relationships

Published state includes `devices`, `subnets`, `vlans`, `racks`, `rackAccessories`, `ipAllocations`, `deviceTypes`, `deviceTypeGraphics`, `deviceLocations`, `serverFunctions`, `installedSoftware`, `managedOptionsCleared` and `softwareTypeExclusions`. These are **observed** keys, not a claim of an exhaustive field inventory. `normaliseState` merges default data with supported incoming state and performs legacy repairs; field-specific retention must be verified rather than assumed.

- **Devices:** observed core fields include `id`, `name`, `type`, `mountType`, `location`, `notes`, `status`, `manufacturer`, `model`, `serialNumber`, `typeDetails`, `virtualPlatform`, `virtualHostId`, `isVirtual`, `ipReserved`, `primaryIp`, `rackId`, `face`, `rackUStart`, `rackUEnd`, `rackUHeight`. Host changes may record `previousVirtualHosts` (`hostId`, `changedAt`, `action`) and `previousVirtualPlatforms` (`platform`, `hostId`, `changedAt`). Existing `handleDeviceSubmit` **rejects changing an existing device's type or virtual identity** with “Device identity cannot be changed. Create a new device instead.” No type-change workflow exists to migrate.
- **Variable details:** `getDetailFieldsForDeviceType` derives fields from device-type profiles and configured catalogues. `typeDetails` can contain supported historical booleans, numbers, strings and other type-specific values; historical top-level service flags such as `serverService_Hypervisor` are read by eligibility/platform logic. Preserve verified legacy and historical values without inventing controls for hidden fields. Replacement hypervisor hosts must meet published active physical-server/Hypervisor-service eligibility.
- **IPAM:** subnets include `id`, `cidr`, `name`, `vlan`, `gateway`, `description` and possible `parentId`/`kind`; VLANs include `id`, `vlanId`, `name`, `description`, `color`, possible `parentId`. `normaliseState` validation requires VLAN number integer 1–4094, unique VLAN record ID, and unique **(parent domain, VLAN number)** combination; the unassigned domain is shared. Subnet save matches VLAN by number **and** parent domain. Legacy VLAN ownership reconciliation refuses ambiguous/orphaned records and checks duplicate numbers within a domain. IP allocations are keyed by IP and can hold `status`, `deviceId`, `hostname`, `notes`, `reservedForDeviceId` and supported historical metadata. Preserve published primary-IP, gateway, subnet membership, reservation and competing-owner checks, including rollback on failed save.
- **Racks:** racks have observed `id`, `name`, `heightU`, `widthMm`, `depthMm`, `depth`, `type`, `location`; accessories include `id`, `rackId`, `type`, `name`, `face`, `startU`, `heightU`, `side`, `portCount`. Preserve device/accessory collisions, U range and face occupancy; vertical `pdu_vertical` and `cable_vertical` use independent left/right 0U rails. Existing alias normalisation maps `fan`→`fan_tray`, `pdu`→`pdu_horizontal`, `vent`→`ventilation`; no other aliases are authorised.
- **Managed catalogues:** configured software/services use stable keys, labels, applicability and archived state. Built-in software suggestions are derived, not automatically saved catalogue entries; `softwareTypeExclusions` affects available suggestions. Renaming a configured service retains its key. Software/service archival is **blocked while assigned** (checks nested and historical top-level flags); otherwise the entry is archived, not hard-deleted. Restoring archived software checks for conflicting available names. Published device details show assigned archived entries, supported by later test evidence.
- **History:** `recordAudit` retains at most 200 events, up to 60 change entries per event plus omitted count; existing categories include devices, subnets, racks, VLANs, allocations, device types and locations. Preserve existing Change History behaviour, not enterprise auditing. Published v1.3.3 History shows historical device details but deliberately **does not** include the removed “Restore Configuration” action.

## 3. Legacy JSON import — verified sequence and boundaries

Published `importData`:
1. Rejects files over 10 MiB; reads UTF-8 JSON and reports parse errors; recursively rejects unsafe object keys `__proto__`, `prototype`, `constructor`.
2. Validates required `devices`, `subnets`, `racks` arrays (50,000 maximum each), `ipAllocations` object (100,000 maximum), optional `rackAccessories` type and backup version metadata. Published v1.3.3 historically recognises missing `caffootBackup` metadata as schema 0 and validates supported metadata-bearing versions. **This describes source history, not Next's newly narrowed import contract:** #215 now supports only fresh v1.3.3 exports.
3. Detects incompatible Access Point mounting/rack assignments **before** normalisation; only when present, asks for explicit mounting choices and applies them to a deep copy. Cancel leaves inventory intact.
4. `normaliseImportedBackupAndPlanLegacyMountRepairs` creates another detached copy. For qualifying desktop/laptop/tablet legacy mount/location inconsistencies, it plans the existing correction (valid non-rack/Desktop mounting, Unknown location, cleared rack placement). It does not change device type or accept unknown mounts/dangling references.
5. `validateAndNormaliseBackupForImport` checks invalid mounts, complete application integrity and rack placement conflicts on the candidate. Only when planned legacy corrections exist does it show the existing review; cancellation stops import.
6. Presents the existing final confirmation with file name and incoming/current inventory counts. Cancel or validation failure leaves current inventory untouched. Published browser code then uses a verified safety snapshot, save verification and rollback. **Next must instead perform an atomic, inventory-only database replacement, leaving accounts, passwords, MFA and permissions untouched, per #215.** Do not reproduce browser snapshot/recovery machinery or its obsolete confirmation wording.

These conditional reviews are not guaranteed for every backup or particular schema version. Do not infer additional correction choices or universal acceptance of arbitrary unknown fields.

## 4. #215 architectural constraints — not additional functionality

- Device owns identity and host/guest relations; IPAM owns allocation, reservation and primary IP; Racks owns placement. Published device objects contain IP and rack fields, but Next must reconstruct the same displayed representation from **one** authoritative database model, not competing copies.
- Backend enforces existing validations atomically, including stale/competing IP and rack writes. Viewing is never locked; #215's short-lived exclusive **device** edit reservation spans Devices/IPAM/Racks, released on Save/Cancel/expiry.
- First administrator chooses credentials and enrols MFA; no hard-coded example username or public signup. Admins manage users; newly created users initially have no inventory access. Enforce approved role permissions and MFA, password changes and self/last-admin safeguards.
- SQLite table names, flexible field storage and API shapes are **unapproved implementation choices**, not requirements. Do not freeze DDL from this reference alone.

## Published save-path verification — device, subnet and rack (2026-10-29)

Verified directly against the published v1.3.3 HTML; **no tests executed**. These are existing behaviour constraints, not new features.

- **Device save (`handleDeviceSubmit`):** rejects missing existing device, changes to existing device type/virtual identity, invalid VM purpose, ineligible new VM host, invalid status, duplicate case-insensitive device name, missing/invalid mounting/location/subnet/primary IP, primary IP outside the selected subnet, and an IP already assigned to another device. Rack-mounted placement requires valid U values and passes `validateRackPlacement`. Hypervisor platform changes affecting guests can require the existing confirmation. The handler snapshots pre-save state; on `setDevicePrimaryIp` / `syncDeviceIpamRecord` failure it restores state and shows the specific device/IPAM cancellation error. Related guest host/platform history is updated when applicable. **Backend implication:** a single atomic device + IPAM + rack + guest-history save, with the same user-facing rejection/confirmation outcomes, plus #215's edit reservation/revision check.
- **Subnet save (`handleSubnetSubmit`):** existing container/address-block path and network path are distinct. Network path checks CIDR (/23–/30), name, VLAN number (1–4094), usable gateway, duplicate CIDR, hierarchy, scoped VLAN conflicts, and gateway assignment/reservation ownership. Existing subnet CIDR cannot change while dependent devices/IP allocations exist. VLAN reconciliation uses number plus parent domain. Save snapshots the state and restores state/selection on failure. **Backend implication:** transactionally validate subnet, VLAN, gateway and dependent allocation state together, preserving the same constraints and rejection messages.
- **Rack save (`handleRackSubmit`):** validates rack name and physical dimensions/type (height 1–100U); lowering rack height is blocked if mounted devices or accessories exceed the proposed height. An existing placement-correction confirmation is conditional. Save snapshots state and restores it and selection on failure. `deleteRack` blocks deletion while devices or accessories remain mounted and otherwise confirms deletion. **Backend implication:** check occupancy/dependencies transactionally and retain the existing conditional correction and deletion decisions.

**Not yet verified in this pass:** full accessory placement handlers, all direct IPAM allocation/reservation/bulk handlers, device deletion guest-resolution branches, and precise persistence/Change History outcomes for each path. Do not treat the three sampled handlers as complete workflow coverage. No database DDL or API implementation is authorised.

## Published direct IPAM, bulk, rack placement and device deletion checks (2026-10-29)

Verified by reading the published v1.3.3 HTML; no tests were run. **These are the existing save/rollback outcomes, not a proposal for new screens.**

- **Direct IPAM (`handleIpSubmit`):** gateway IPs are protected. When an address is a device's primary IP, IPAM permits editing its notes but rejects changing its status/hostname or releasing an orphan reservation; device editing owns primary assignment changes. Setting an address Available also refuses to release an active device primary assignment. An allocation's device ID must correspond to the device actually using that IP. Failed persistence restores the previous allocation (or deletes the newly created one). Next must enforce these guards against shared authoritative IPAM/device records, including concurrent edits.
- **Bulk IPAM (`handleBulkIpSubmit`, `applyBulkIpChanges`):** the existing planner computes eligible changes and a review/confirmation before applying them. Apply recalculates the plan; missing/expired preview or no eligible changes fails. Published browser code creates a pre-bulk local safety snapshot and restores the prior in-memory inventory on save failure. Per #215 Next must preserve review, eligibility and all-or-nothing outcomes via a SQLite transaction **without** reproducing the browser safety-snapshot mechanism or its obsolete wording.
- **Rack accessories (`validateRackAccessoryPlacement`):** validates existing rack/face, integer U bounds and height; ordinary front/rear accessories cannot overlap devices or other nonvertical accessories. Vertical PDU/cable rails require left/right side and only conflict with another vertical rail occupying the same rack, face, side and U range. `requestRackAccessoryDeletion` confirms and restores prior state on save failure; `moveRackAccessoryToPosition` rejects vertical drag moves and validates ordinary placement before saving. `moveDeviceToRackPosition` validates placement and restores prior position on save failure. Preserve existing accessible click-to-move and drag/drop behaviour.
- **Device deletion (`deleteDevice`):** when guests depend on a host, existing per-guest choices precede a separate host-deletion confirmation. It rechecks whether inventory changed during guest review. Supported choices unassign, retire or move each guest to an eligible replacement host, preserving relevant host/platform history. It releases related IP allocation ownership and reservations and removes the device; failed persistence must leave prior inventory intact. The current deletion confirmation contains browser-era “Export a backup first” wording, which #215 explicitly permits minimally correcting for Next; the confirmation decision and its inventory counts/relationships remain.

**Transaction boundaries to validate during later design:** a single direct-IPAM update, bulk range operation, accessory/device rack move, or device deletion with guest and allocation consequences must commit completely or not at all. Check #215's access control and device-edit reservation wherever an operation affects a device; do not invent new UI prompts. These source checks still need retained-test reconciliation before final schema/API approval.

## Source-confirmed IP ownership and history persistence details (2026-10-29)

Directly verified against published v1.3.3 `setDevicePrimaryIp`, `syncDeviceIpamRecord`, `saveState`, `recordAudit` and `validateApplicationState`. This refines the *candidate* schema only; no implementation approved.

1. **Existing source authority vs proposed database authority:** v1.3.3 explicitly calls the device the source of truth for its primary-IP allocation and mirrors the assignment into `ipAllocations`. Issue #215 intentionally changes the **internal** owner to IPAM while preserving the visible device/IPAM behaviour. Thus the backend should represent the device-primary-IP link once in IPAM and derive `device.primaryIp` and `device.ipReserved` when assembling the existing front-end shape. This is a **proposed projection**, not yet final DDL.
2. **Changing primary IP:** before releasing the old address, `setDevicePrimaryIp` checks duplicate device usage, gateway type eligibility (Firewall, Router, Layer 3 Switch), configured subnet membership, conflicting `deviceId`, conflicting `reservedForDeviceId`, and unowned Reserved/Assigned status. If validation passes, the old owned allocation is set `Available` and its other IPAM fields are retained; the new record is assigned to the device, status `Reserved` or `Assigned` based on `ipReserved`, and hostname/notes are preserved as applicable. Device rename invokes `syncDeviceIpamRecord`, which updates allocation hostname to the device name and preserves notes. **Implication:** do not cascade-delete or overwrite the old allocation on IP change; keep independent reservations distinct from current primary assignment.
3. **Live integrity:** `validateApplicationState` validates subnet hierarchy/type, unique subnet/device IDs and VLAN uniqueness within parent address-block domain. Physical schema uniqueness must respect this domain scoping; application-level checks still required for hierarchy/overlap and cross-record constraints.
4. **History nuance:** `saveState` writes the inventory browser snapshot, then invokes `recordAudit` separately; `recordAudit` appends at most 60 changes per event and retains the most recent 200 events. A history-storage failure can leave inventory saved with an error toast. #215 requires backend Change History and atomic inventory operations, but **does not explicitly decide whether a history-write failure must roll back an otherwise valid inventory save**. Do not silently assume exact browser persistence failure semantics carry into SQLite; resolve at API/transaction sign-off without introducing a new visible history workflow.

**Next verification tasks:** enumerate actual published device/IPAM/rack field names from create/update/import paths (including historical fields), verify v1.3.3 backup round-trip for each, then map them into typed columns versus scoped flexible JSON without losing or reinterpreting supported data. Confirm history failure semantics with the owner if source evidence and #215 do not settle the database transaction decision. No schema migration or tests executed.

## Batched source reconciliation: integrity, managed catalogues and history (2026-10-29)

Additional published v1.3.3 source inspection, **not newly run tests**:

- **Live integrity is stricter than simple foreign keys:** `validateApplicationState` rejects missing/duplicate device/subnet IDs, duplicate device primary IPs, incompatible mount types, retired `Blank` locations, primary IPs without a configured subnet, device/IPAM status or ownership mismatches, IP allocations outside all subnets, allocations linked to missing/wrong devices, missing racks for mounted devices, non-rack mount types with rack IDs, inconsistent start/end/height U, and VLAN duplication within the same parent address block. These are explicit acceptance assertions for the backend and cannot be reduced to basic SQLite `FOREIGN KEY` constraints alone.
- **Source confirms there is no permitted persistent device-primary-IP mismatch at save time:** `normaliseState` may accept certain legacy forms before integrity checking, but `saveState` always calls `validateApplicationState`. Earlier candidate-schema notes about importing historical devices without matching allocations must therefore distinguish rejected invalid exports from accepted import repair flows. Do not silently create a permissive orphan-primary-IP mode.
- **Managed software elements:** `installedSoftware[]` configured entries use stable `key`, `label`, `deviceTypes[]`, and optional `archived`. Built-in overrides are stored under built-in-derived keys. Removing an assigned entry is blocked when either `device.typeDetails[key]` or legacy `device[key]` is true; unused entries are archived rather than destroyed. Restoration checks case-insensitive active-name collisions. A device may display historical archived assignments.
- **Managed server service elements:** `serverFunctions[]` entries use `key`, `label`, optional `archived`; built-in overrides and custom keys are retained. Device assignment checks both nested `typeDetails[key]` and legacy top-level `device[key]`; preserve both on migration. Rename/restore must retain stable keys and enforce existing duplicate-name restrictions.
- **Historical device details:** `previousTypeDetails[]` entries are rendered with `type` and `details{}`; `previousVirtualHosts[]` records `hostId`, `changedAt`, `action`. Preserve arrays as authored and the existing read-only display, rather than normalising them into new operational assignments.
- **Change History precise diff categories:** `auditChanges` reports `devices`, `subnets`, `racks`, `vlans` by ID, `ipAllocations` by IP key, plus managed `deviceTypes` and `deviceLocations` list changes. Each Updated record lists at most **16 changed field names**, and the event retains at most 60 changes (200 events overall). It does **not** explicitly diff `rackAccessories`, `serverFunctions`, `installedSoftware`, or `deviceTypeGraphics` as independent categories. Preserve the existing visible history semantics; do not assume a generic all-table audit is compatible.
- **Inventory reset:** the published clean reset sets `managedOptionsCleared=true` on the default inventory. This setting must remain distinguishable from an empty managed catalogue when reconstructing the inventory view; do not infer reset from an empty table.

**Candidate schema refinement:** `devices` and managed catalogue records need a safe per-record representation of legacy top-level dynamic keys and nested `typeDetails`; indexed typed columns should cover stable relationships, but no user data may be dropped during conversion. History should be generated from the *projected v1.3.3 inventory shape* with the same diff categories/limits, not from generic SQL row changes. Confirm import acceptance using real v1.3.3-export fixtures, then specify DDL and endpoint transactions only after separate authorisation. No application changes, tests, or approvals implied.

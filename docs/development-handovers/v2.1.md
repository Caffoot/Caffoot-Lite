## What we've decided

- **Appearance:** follow the exact approved screens, shared full-width layout, straightforward sidebar, top-right My Account control, readable typography and upright Caffoot logo. Don't redesign accepted screens.
- **Existing behaviour:** v2.0.3 is the functional baseline. Preserve Devices/IPAM/Racks, VM/host and physical Hardware rules, separate permissions, Rack front/rear/L/R/0U and print behaviour, accounts, MFA, imports, help links and installation data.
- **Technology:** **We've chosen Svelte** for the v2.1 interface after reviewing the isolated Device Details pilot. Small, reusable components should be easier to maintain and extend than the existing large HTML file. Keep Python, SQLite and simple self-hosted Docker installation; compile Svelte into static assets served by Python. This does **not** approve wholesale migration or any live-data changes.
- **Additional work:** optional personal details/profile images, optional administrator SMTP and removal of the Audit Trail's 200-event limit are agreed areas. Their precise storage, security, permissions and behaviour need separate specifications before related code changes. New events should be retained indefinitely by default.
- **Working rules:** use friendly British English, small reviewable batches and proportionate tests. Agree each batch before writing code; approve merging and publication separately. Do not publish public development Docker/GHCR images.

The [new issue](https://github.com/Caffoot/Caffoot-Lite/issues/266) is the concise working plan. Refer to the approved design index and [Development Guide](../development-guide/README.md) for detail instead of duplicating it here.

## Stage 1 — Device Details pilot

The agreed Stage 1 scope is a **small, isolated Svelte evaluation** based on the accepted [Devices Details & Forms Batch 04 design](../../future-design/approved/devices-details-forms-batch-04.html).

The pilot was merged through [PR #268](https://github.com/Caffoot/Caffoot-Lite/pull/268). It uses fictional records and cannot save anything to the real application. We checked:

1. **Visual match:** typography, spacing, navigation, forms, tabs, responsive layout and keyboard accessibility against the approved HTML.
2. **Functional match:** physical-device versus VM controls, representative editing/form states, user permissions and the existing API contract. Do not silently change save rules or bypass the backend.
3. **Practicality:** safe rendering, build complexity, performance, testability and straightforward serving of the compiled frontend from the existing Python/Docker installation.
4. **Decision:** record what worked, what didn't and whether Svelte is the right approach before planning application-wide integration.

**Checks on 3 November 2026:** GitHub's Svelte build, non-saving static boundary checks, Chromium tests (1536, 1280 and 390 px), documentation check and Git history secret scan all passed on PR #268. [Browser screenshots](https://github.com/Caffoot/Caffoot-Lite/actions/runs/41619894409) are attached to the GitHub Actions run. The screenshots were reviewed and described as looking great, with no noticeable visual difference from the approved design. **Svelte was then chosen as the v2.1 frontend direction.** Actual backend/API integration, full accessibility and functional parity are untested and deliberately outside this pilot.

**Next:** the read-only integration was visually accepted and both PR merges were authorised. Before extending the application beyond this safe foundation, agree a new scoped batch for real Edit/Save, complete forms/catalogues and cross-section functionality. None of those are included in this stage.

## Read-only connection to the existing application

The agreed read-only batch is recorded in [PR #269 — Read real device data](https://github.com/Caffoot/Caffoot-Lite/pull/269), developed from the pilot merged through PR #268. It is deliberately **additional**, not a replacement for any published screen.

- The new Svelte page uses the established Python Devices endpoints and saved SQLite record fields, including VM host links and virtual hardware. It can only **read** information.
- It appears under a separate development route, disabled by default. The Python server checks the existing session and Devices permissions before serving the page or its assets.
- Rack data is loaded only with Rack access. The page doesn't request the IPAM collection or send any POST requests. There are no Edit, Save or Delete controls.
- The existing `/setup`, `/inventory`, authentication, MFA, device editing and Dockerfile have not been replaced. The normal Docker image does not include the Svelte preview build files.

**Checks on 3 November 2026:** the Svelte static build, frontend permission tests, Python route tests, a real HTTPS/SQLite Chromium test with disposable admin/Devices-only/IPAM-only accounts, and the **original application browser regression** all passed. The backend suite, documentation check, history secret scan and first pilot checks also passed. The [GitHub Actions run](https://github.com/Caffoot/Caffoot-Lite/actions/runs/41631825472) includes screenshots to review. The test data is fictional, but it is saved and retrieved through the **real backend and SQLite API** rather than hard-coded in the frontend.

**Still outstanding:** live Edit/Save and exclusive edit reservations; full Devices form and catalogue parity; broader permissions, IPAM/Rack synchronisation and a deployment/upgrade acceptance check. The product owner visually accepted the read-only screenshots and authorised both merges. Don't mark these as complete merely because a read-only screen passed.

## Stage 2A — first integrated Svelte workspace (in progress; not accepted)

The product owner authorised a narrowly scoped, production-facing **development batch** on 3 November 2026. This is not permission to merge or publish a release.

- Build reusable Svelte sidebar and header components following the 12 approved visual sources.
- Serve a separately built, authenticated workspace from Python at `/workspace/`. Keep `CAFFOOT_SVELTE_WORKSPACE` **off by default** and continue to serve all existing functionality at `/inventory`.
- Display the established read-only Devices view with real saved data and independent section permissions. Other sidebar destinations and My Account route directly to their existing working screens, without silently substituting incomplete Svelte pages.
- Compile the workspace during Docker build in a Node builder stage, then copy only static files to the Python runtime image. Do not package the fictional-data pilot or add Node to the running container.
- Check desktop, medium and mobile screenshots, proper role-aware navigation, host/VM behaviour, route security, original browser functionality, backend tests, and a disposable Docker build.

**Acceptance remains outstanding:** checks must actually pass, the owner must review browser evidence, and merges are a separate decision. Do not call Stage 2 complete: no existing production screen is replaced and live Svelte editing remains out of scope.

## How to continue in a new chat

1. Read [issue #266](https://github.com/Caffoot/Caffoot-Lite/issues/266) and this handover for the latest agreed stage.
2. Check current `main`, open PRs and relevant GitHub checks. Respect anything merged since this checkpoint.
3. Use the exact [approved designs](../../future-design/README.md) for appearance and the current application/tests for functionality.
4. Agree the next small batch, work only on that scope, run relevant checks and record the actual result.
5. Update this handover and #266 when a batch is accepted. Nothing merges or publishes merely because a mock-up or automated check looks good.

**Updated:** 3 November 2026

We've published [v2.0.3](https://github.com/Caffoot/Caffoot-Lite/releases/tag/v2.0.3) and finished the preceding security and functional-baseline work. The simpler **Publish Caffoot Lite** workflow is established.

At this checkpoint, there is **an isolated, non-saving Svelte pilot** under draft [PR #268](https://github.com/Caffoot/Caffoot-Lite/pull/268), but **no production frontend migration, database migration, Docker preview image or release**. The closed, unmerged redesign PRs #229 and #230 remain historical and should not be revived.

## What we've decided

- **Appearance:** follow the exact approved screens, shared full-width layout, straightforward sidebar, top-right My Account control, readable typography and upright Caffoot logo. Don't redesign accepted screens.
- **Existing behaviour:** v2.0.3 is the functional baseline. Preserve Devices/IPAM/Racks, VM/host and physical Hardware rules, separate permissions, Rack front/rear/L/R/0U and print behaviour, accounts, MFA, imports, help links and installation data.
- **Technology:** Svelte is a promising direction, **not yet the selected framework**. Evaluate it first through a small, isolated Device Details pilot. Keep the existing Python/SQLite backend and simple Docker installation unless a change is separately approved.
- **Additional work:** optional personal details/profile images, optional administrator SMTP and removal of the Audit Trail's 200-event limit are agreed areas. Their precise storage, security, permissions and behaviour need separate specifications before related code changes. New events should be retained indefinitely by default.
- **Working rules:** use friendly British English, small reviewable batches and proportionate tests. Agree each batch before writing code; approve merging and publication separately. Do not publish public development Docker/GHCR images.

The [new issue](https://github.com/Caffoot/Caffoot-Lite/issues/266) is the concise working plan. Refer to the approved design index and [Development Guide](../development-guide/README.md) for detail instead of duplicating it here.

## Stage 1 — Device Details pilot

The agreed Stage 1 scope is a **small, isolated Svelte evaluation** based on the accepted [Devices Details & Forms Batch 04 design](../../future-design/approved/devices-details-forms-batch-04.html).

The pilot is implemented for review on [draft PR #268](https://github.com/Caffoot/Caffoot-Lite/pull/268). It uses fictional records and cannot save anything to the real application. We checked:

1. **Visual match:** typography, spacing, navigation, forms, tabs, responsive layout and keyboard accessibility against the approved HTML.
2. **Functional match:** physical-device versus VM controls, representative editing/form states, user permissions and the existing API contract. Do not silently change save rules or bypass the backend.
3. **Practicality:** safe rendering, build complexity, performance, testability and straightforward serving of the compiled frontend from the existing Python/Docker installation.
4. **Decision:** record what worked, what didn't and whether Svelte is the right approach before planning application-wide integration.

**Checks on 3 November 2026:** GitHub's Svelte build, non-saving static boundary checks, Chromium tests (1536, 1280 and 390 px), documentation check and Git history secret scan all passed on PR #268. [Browser screenshots](https://github.com/Caffoot/Caffoot-Lite/actions/runs/41619894409) are attached to the GitHub Actions run. Desktop and mobile screenshots have been inspected, but **the product owner has not yet accepted the pilot's appearance**. Actual backend/API integration, full accessibility and functional parity are untested and deliberately outside this pilot.

**Next:** review the actual screenshots and interaction; agree any visual refinements. Then make a separate choice about Svelte and any later production implementation. The draft PR must not be merged merely because the checks passed.

## How to continue in a new chat

1. Read [issue #266](https://github.com/Caffoot/Caffoot-Lite/issues/266) and this handover for the latest agreed stage.
2. Check current `main`, open PRs and relevant GitHub checks. Respect anything merged since this checkpoint.
3. Use the exact [approved designs](../../future-design/README.md) for appearance and the current application/tests for functionality.
4. Agree the next small batch, work only on that scope, run relevant checks and record the actual result.
5. Update this handover and #266 when a batch is accepted. Nothing merges or publishes merely because a mock-up or automated check looks good.

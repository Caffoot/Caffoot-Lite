# Caffoot Lite — Instructions for coding agents

These rules apply to all AI-assisted development in this repository. Read them before editing. The product owner retains final authority. Approved GitHub issues, pinned designs, specifications and explicit owner decisions are authoritative.

## Non-negotiable working rules

1. **Follow the approved plan exactly.** Implement only the authorised scope. Do not reinterpret requirements, replace approved HTML with approximations, redesign interfaces, or invent features.
2. **Ask rather than assume.** If a material requirement is unclear and the decision would change approved behaviour, ask the product owner before proceeding. Do not silently choose an alternative.
3. **Use the simplest approved approach.** Do not introduce frameworks, new architectures, refactors or additional dependencies without explicit approval. Do not confuse permission to implement a feature with permission to redesign it.
4. **Preserve working behaviour.** Protect existing data, installation and upgrade compatibility, URLs, APIs, permissions, authentication, security and all approved functionality unless expressly instructed otherwise.
5. **Control scope and cost.** Complete the defined task rather than repeatedly expanding investigation. Reuse existing evidence and completed tests. Avoid duplicated work, speculative improvements, repeated whole-suite runs without a reason, and unnecessary tool calls. Resource or credit limits never justify an unapproved shortcut.
6. **Commit and push meaningful checkpoints early.** After a coherent change, run appropriate focused checks, commit and push to the explicitly authorised development branch before further lengthy work. Clearly label any partially tested checkpoint; never treat it as accepted. Never leave substantial completed work solely in an ephemeral workspace.
7. **Test proportionately, then meet the acceptance criteria.** During development run checks relevant to each change; complete all explicitly required functional, security, Docker and visual acceptance checks before declaring the work ready. Passing automated tests alone does not prove visual fidelity.
8. **Report only verified results.** Distinguish implemented, committed, pushed, tested, failed, untested and owner-approved. Provide exact commit SHAs and real evidence. Never claim a build, test, visual match or release succeeded without verification.
9. **Stop at a genuine blocker.** If the approved approach cannot work, explain exactly what prevents it and the minimum proposed change; obtain explicit owner approval *before* deviating. Do not disguise a workaround as equivalent.
10. **Respect the delivery boundary.** Do not modify `main`, merge PRs, publish images or releases, or change unrelated branches/issues unless explicitly authorised. A finished task is the agreed outcome, not a large diff, high test count or long-running investigation.

## Stop-and-simplify trigger

If the product owner **or the assistant** says "this is too complicated", "this is getting silly", or words to that effect, **stop repeating the current procedure**. Treat the comment as an instruction to investigate the simplest safe, supported route to the agreed outcome, not as permission to drop security or acceptance checks.

- State what has already been completed and preserved, what is actually blocked, and why. Do not restart finished work or repeat failed approaches without new evidence.
- Check the available tools, access permissions, repository settings and alternative supported workflows before requesting further manual steps. Prefer direct access and the fewest straightforward owner actions.
- Explain the viable options, their security and delivery trade-offs, and recommend the least complicated one that preserves the approved requirements. Distinguish genuine restrictions from optional process.
- If the agreed approach must change, **obtain explicit owner approval before changing the route, scope, security boundary or release plan**. Document the chosen route, failed approach and exact next step in the relevant handover so the same obstacle is not revisited.

## Efficient development and final verification

- **Do not spend coding time watching CI.** Implement the approved change, run only relevant focused tests, commit and push the checkpoint, report the PR link and test results, then stop. Do not poll GitHub Actions, repeatedly call `gh run view`, wait for workflows to finish or repeatedly rerun passing suites. Independent reviewers monitor CI outside the coding session.
- **Draft PRs are for development.** The complete backend, Docker Compose and multi-browser regression workflows are deferred while a PR is a draft. Run the necessary focused checks locally to establish that each changed behaviour, permission and data safeguard works. Record anything not tested. Do not treat a skipped full check as a pass.
- **Ready For Review is the final CI checkpoint.** After the implementation, essential documentation and required screenshots are complete, mark the PR Ready For Review to trigger the full existing checks. A subsequent change to application code requires the new head to pass its required checks before merge. Do not rerun these full suites automatically on each `milestone-1` merge: the PR's reviewed code receives the full check before merge. Keep manual and publication checks available. Never push directly to `milestone-1` to bypass PR review; if an exceptional direct push is authorised, run the complete backend, Docker and browser workflows manually. Before merging, ensure the final checks apply to the current integration base and PR head; if the base has changed materially, repeat the affected acceptance checks.
- **Evidence-only follow-ups are narrow.** Review only the new evidence and affected files; do not regenerate unrelated screenshots or repeat broad local testing. Record any check affected by the changed PR head.
- **Never weaken acceptance to save credits.** Permissions, persistence, security, release and compatibility requirements still apply. If a focused check cannot establish safe behaviour, run the necessary wider check and explain why. The owner alone approves scope, merges and releases.

## Verification scope and resource approval — all development

These restrictions apply to every development, investigation, review and acceptance session, not just the current milestone.

- **Cloud desktop and computer use require explicit prior owner approval.** Do not launch or use cloud desktop skills, remote graphical desktop sessions or computer-use tools as an alternative verification method without approval for that specific purpose. Existing approved local automated browser fixtures are not prohibited.
- **Respect acceptance stages.** Keep native/manual acceptance and other explicitly deferred checks in their approved stage. An outstanding item in a coverage matrix is not permission to bring it forward. Record deferred items as outstanding, never as passed; use the agreed acceptance route when authorised.
- **Ask before resource-intensive deviations.** If the approved verification approach is insufficient and a resource-intensive investigation outside that approach is proposed, stop first. Report the exact blocker, evidence already obtained, the minimum necessary next step and its likely resource implications; seek explicit owner approval before proceeding.
- **Reuse verified evidence.** Do not repeat previously verified checks or browser journeys without a documented technical reason, such as an affected code change or invalidated evidence. Limit reruns and new captures to the affected scope while meeting all mandatory acceptance requirements.
- **Do not independently expand verification scope.** Permission to develop or complete a batch does not authorise unrelated investigations, additional acceptance stages or alternative resource-intensive methods. If scope or stage is uncertain, stop and ask. Preserve meaningful checkpoints and report what remains outstanding.

These restrictions do not waive any security, functional, accessibility, visual, compatibility or release acceptance requirement.

## Mandatory Documentation Quality Standard

**Every new or materially changed feature must have comprehensive, accurate user and administrator instructions written alongside the implementation.** This applies to existing and future Caffoot Lite versions, including the approved Stage 1–3 draft guides and forthcoming Stage 4–6 features. Do not leave the guide until the end of a milestone or treat a brief feature summary as sufficient.

- Write approachable, thorough **British English** for someone using Caffoot Lite for the first time; explain necessary terminology and the purpose of each task. Use the established long-form [v2.2 draft guides](docs/how-tos/features-and-instructions/v2.2/README.md) as the quality reference, without mechanically copying irrelevant sections or padding text.
- For every applicable workflow, document its **prerequisites, relevant permissions and feature switches; exact navigation, buttons and fields; numbered instructions; states and expected results; realistic fictional examples; what happens on Save, Cancel or rejection; common problems and troubleshooting; privacy/security boundaries; and links to related tasks**. Cover complete journeys across related features where needed.
- Use **genuine screenshots of the actual, implemented application for the correct version**, matching approved interface designs and current controls, with helpful captions and accessible alternative text. Verify provenance and obtain required owner visual/publication approval. If suitable current evidence is not yet available, record the gap explicitly; never invent a screenshot, use an unapproved HTML preview as proof or imply an outdated image is current.
- Maintain **version-specific truth**: unreleased v2.2 instructions must remain clearly marked draft; archived guidance must describe its own version. Do not publish unverified install, upgrade, backup, restore or release claims. Preserve dated decisions and historical evidence instead of rewriting history.
- Apply the same commitment to **clear, complete and task-appropriate explanations** in installation, administration, recovery, security, troubleshooting and developer reference documentation. A short issue update, PR summary or historical checkpoint need not become a long guide; detail must match what a reader needs to do safely and confidently.
- Review the affected guide and its links, wording, permissions and screenshot evidence as part of the feature PR; record incomplete documentation or deferred visual acceptance honestly. **Documentation approval does not waive functional tests or independent product-owner merge/release approval.**

The [contributor guide](CONTRIBUTING.md#documentation-is-part-of-the-change) applies this requirement to all maintainers, contributors and AI-assisted work.

### Documentation And Repository Care

Documentation is part of feature completion. Write and maintain comprehensive, accurate, version-correct British-English user and administrator instructions alongside every new or materially changed feature. Explain the task, prerequisites, permissions, feature switches, navigation, fields, numbered actions, expected outcomes, cancellation/rejection, realistic fictional examples, troubleshooting and relevant safety/privacy boundaries. Detail must serve the intended reader; do not pad short updates or duplicate maintained guidance.

Keep instructional and release-facing content focused on using Caffoot Lite. Review every paragraph, caption, callout and link. Exclude temporary batch/stage/checkpoint notices, internal issues/PRs, AI/development commentary, screenshot-production details and testing/review/acceptance/provenance links. Retain useful explanations, prerequisites, permission/security warnings, troubleshooting, examples, accessible captions and alternative text, related instructional links and necessary truthful version/draft notices.

Use genuine, correct-version, approved desktop light-theme application screenshots beside the relevant instructions. Do not use generated images, mock-ups, standalone HTML previews, misleading older states, or dark/mobile images as instructional illustrations. Reuse suitable existing images where possible; capture work and resource-intensive verification require the applicable owner authorisation. Preserve original images, hashes, manifests, mobile/dark development evidence and historical decisions separately. Record missing or outdated illustrations in development records without implying that visual or publication approval has passed.

Maintain repository organisation, indexes, navigation, links, README, release notes and relevant installation, deployment and configuration guidance with the same care as application code. Maintain supported version-specific guides, including archived releases, and preserve release history, existing installation/image references and compatibility URLs. Clearly distinguish unreleased features and isolated-review procedures from published production guidance; never invent successful installation, upgrade, backup, recovery, security or release results.

Keep release inventories and documentation traceable to approved requirements, actual application behaviour and revision-specific verification evidence. Reconcile corrections when they occur. Keep traceability in the development/evidence register pointing to the guide so instructional readers need not navigate internal records. Seek separate owner approval before destructive removal or restructuring of obsolete or duplicated material.

Use approved version-specific documentation as the authoritative source for corresponding website content. Website implementation, synchronisation, deployment and publication require their own approval; documentation completion does not authorise them.

Include documentation completeness and repository accuracy in feature acceptance and release readiness. Record deferred work honestly. Preserve all existing application, functional, permission, security, accessibility, visual, compatibility, native/manual, testing and release gates. Independent review and explicit owner merge/release approval remain separate requirements.

## Target-Version Branch And Release Preparation Standard

Apply this standard to every future release, not just Milestone 01. The owner explicitly agrees the target release and integration branch at the start of each milestone (for example, v2.3 on `milestone-2`, if approved). Keep `main` and the current published release accurate and unchanged until their separately authorised release transition.

- Maintain the milestone branch's active release-facing files for its own target version throughout development: README, installation instructions, root Portainer/Compose configuration, permanent version-specific user and administrator guide locations, navigation and Help & Guides links, About/version presentation, release notes and relevant release tooling. Update them alongside approved feature work; do not leave a large version-conversion or file-relocation exercise until publication.
- Treat the whole active development repository as documentation and implementation for its approved target version, not as a mixture of the target and the preceding published release. README, installation/configuration, current guides/indexes, About/Help & Guides, release notes, roadmap, current development status, contributor guidance and release tooling must focus on that target from milestone start. Use a concise truthful target-version unreleased/non-production notice where appropriate; do not repeatedly identify the preceding version as the current release, embed its installation instructions in active target guidance, or require such wording in candidate checks. Keep previous release documentation in history and preserve necessary compatibility notices/URLs, upgrade/migration prerequisites, actual evidence, immutable references and legacy format identifiers. This applies throughout development, not only at publication.
- Clearly identify the candidate as unreleased without implying public availability. Prepare future image/tag/link destinations without claiming that they are already available. Never present an unverified installation, upgrade, backup or recovery procedure as supported or passed. Retain the separately approved publication boundary and strict finalisation gate.
- Preserve older published guidance, historical releases and evidence, legacy format identifiers and compatibility URLs. Archive superseded active release files in their agreed locations; obtain separate approval before destructive changes or restructuring.
- Verify candidate-version consistency in the normal read-only development/PR checks. Keep explicit publication checks strict and separate; no relaxation of owner approval, protected-main, exact-revision, required tests, version, collision, compatibility, architecture or image-availability safeguards. Changes to these checks require their own scoped approval.
- Before the final acceptance and release review, complete all practicable target-version preparation and reconcile outstanding evidence. Record the exact genuinely release-dependent actions that remain; avoid last-minute substantive documentation, configuration or version changes. Recheck affected evidence if the reviewed candidate changes.
- Preparing a milestone branch does not authorise a merge, deployment, tag, image, release, website publication or marketing activity. Preserve the approved acceptance and publication sequence and obtain each separate owner approval.

### Repository Lifecycle And Mandatory Release Finalisation

- At the start of each separately approved milestone, keep active user/administrator guides for its target version in the agreed version-specific directory and a clear documentation index. Archive the preceding published guides, associated instructional screenshots and superseded installation/configuration material under the appropriate version-specific location in `docs/historical/`. Keep prior tags and immutable version-pinned application help links valid. Where older installations use mutable main-branch URLs, retain minimal compatibility notices at those paths linking to the correct archived guide; check both existing legacy path variants and any required anchors. Never silently substitute newer-version instructions. Agree exact moves and compatibility verification before implementation.
- Keep current architecture, API/function references, operational runbooks, coding standards, active milestone plans and required application source/assets/tests in their active locations. At milestone completion, after the relevant acceptance and release records are genuinely complete, archive completed plans, handovers, batch reviews, historical screenshots and development evidence by version, preserving provenance, binary identities, relevant links and historical wording. Do not delete evidence or relocate it while still needed by an active gate. Obtain owner approval for the exact archive scope; do not undertake speculative repository-wide restructuring.
- **Mandatory draft-notice removal gate for every release:** during final documentation reconciliation, inventory every active release-facing notice and reference to the candidate being draft, unreleased, private-review-only, or the prior version being current. Prepare the final wording using actual accepted installation, upgrade, recovery and feature evidence; retain truthful candidate status until the owner explicitly authorises final release preparation. After all required acceptance, offline website preparation and independent audit gates, and before the separately authorised merge to main and publication workflow, complete a reviewed release-finalisation change removing or reconciling every obsolete candidate notice (including each individual user/administrator guide, README, installation instructions, configuration comments, release notes, indexes, About/Help & Guides and active status/support references). Do not replace a previous-version number indiscriminately or remove historical notices/evidence. Pin help links to the final accepted version-specific guide content and verify their actual destinations.
- Prepare the final intended public image/tag references in the reviewed release files before strict publication preflight; availability remains conditional on the owner-authorised publication workflow successfully building/pushing the exact tested revision and verifying platforms and anonymous public access. Do not require the public image to exist before the workflow that creates it, or announce a release prematurely.
- Make the draft-notice inventory and its resolution a recorded release acceptance criterion, not a memory-dependent reminder. Require a scoped residual-notice/link/version scan over all active release-facing files, appropriate automated negative tests for leftover candidate notices and incorrect versions/configuration, strict explicit-version preflight, and independent review of the exact final revision. Preserve historical/compatibility content that is intentionally version-specific. Record the results and any genuine exceptions in the master milestone tracker and release PR; stop if unresolved. Recheck any acceptance or audit evidence affected by final changes. Only after successful publication verification may the website, public download instructions and launch announcements describe the release as available, with their separate approvals.
